# Compiler audit and proposed roadmap adjustments

Reviewed source at `a202b734`, after the parameter-based effect worklist
checkpoint. This is an architectural review with source inspection, focused
capability probes and an independent hosted seed build. It is not a line-by-line
verification of every implementation or a fresh green full-suite certification.
Recommendations below are proposals; they do not redefine the language or mark
Phase 1 complete.

The [September 30 follow-up](#follow-up-2026-09-30) below audits `7dcf7672`
and records David's subsequent design clarifications. The earlier measurements
and workflow/capability observations remain historical; in particular, the
release-gating gap described below was fixed before the follow-up revision.

## Assessment

The direction is sound: retain value semantics, checked facts, explicit places,
ordinary Dewy libraries, the Dewy/µDewy split and the dependency-free Python
reference. Native self-hosting, differential checks, deterministic cleanup and
the binary output path are substantial foundations. Do not replace them with a
new compiler architecture merely because the current implementation is slow.

The largest obstacle is now the cost of advancing those foundations. Too much
work still creates, copies and reinterprets small aggregate objects; multiple
consumers rediscover related facts; broad validation is expensive; and current
capabilities are mixed with historical plans in the documentation. Continuing
one source shape at a time indefinitely would make Phase 1 an expanding queue
rather than a milestone.

I recommend a bounded correctness closure with a focused throughput campaign
inside the remaining Phase 1 work, then a small Phase 2 library-enabling slice. These are
engineering changes to the roadmap's execution, not a change to Dewy's goals.

## Performance: remove work before tuning how it runs

### Allocation frequency is at least as important as copied bytes

The historical profile's 402 million allocations would require 40.2 million
allocations per second to fit a ten-second *whole build*. That permits only
25 ns per allocation before parsing, checking, lowering or backend work. At
3.4 GHz that is roughly 85 cycles. It is not a lower bound on compiler time:
many of those allocations are unnecessary. It demonstrates why making one
allocator call a little cheaper cannot deliver the intended result.

The source is about 3 MB, while aggregate traffic is tens of GB. Allocation
counters are not literal DRAM bandwidth: they include recycled blocks, size
classes and repeated temporary storage. Nevertheless, this disparity justifies
eliminating whole classes of representation work. Measure visit counts, state
entries, allocations, detachments and bytes alongside wall time. Do not infer
an achievable compiler time from source bytes divided by peak memory bandwidth.

Specific remaining candidates:

| Candidate | Current evidence | Proposed next action |
| --- | --- | --- |
| Empty aggregate storage | `lower.array_memory` avoids an empty data buffer but still constructs a private descriptor. The older profile attributed 73.7 M descriptor allocations to `[]`. | Introduce an immutable empty representation behind the existing value interface, materializing a private owner on mutation. Check places, reserve, cleanup, nested fields and allocator ownership; a shared descriptor must never become writable. |
| Small temporary collections | Parser candidates, child worklists, effect paths and statement prefixes frequently allocate short arrays. Fixed scalar frame placement already exists; general growable scratch lists are a different case. | Use bounded inline storage with a measured spill path for proven nonescaping scratch owners. Cover both compilers' semantics without requiring equal storage costs. |
| Mutable analysis snapshots | Facts and branch states still own arrays, records and dictionaries. COW avoids some immediate copying but can defer a large detach. | Profile the remaining state operations, use one owner for mutable construction, borrow immutable inputs, and transfer completed results. Prefer flat IDs and compact entries where they remove ownership trees. Do not globally replace value semantics with aliases. |
| Repeated analysis discovery | Local places, lifecycle handling, place contracts, bounds preparation, public effects and lowering consume overlapping graph/route information. | Inventory the repeated traversals and share a revision-bound analysis context where semantics match. Propagate changed summaries by dependency; retain distinct modes when they differ, such as raw exposure and `value_casts_escape`. |
| Intermediate representations | Dewy emits µDewy tokens which a parser port records as backend operations; direct object writers still consume generated assembly strings. | Remove one measured intermediate at a time, driving the existing operation protocol directly. Preserve text/reference routes and target/ABI checks. Do not add another independently maintained IR merely to bypass one format. |
| Executing compiler code | The direct backend already has local register allocation and an expression register cache. Its generated compiler has historically been slower than a C-built one. | Profile generated compiler instructions/calls/spills, then improve the direct backend on representative kernels. Measure emission time and runtime throughput separately. An optimization that slows compilation but improves subsequent compiler generations may still be worthwhile. |

Two older recommendations are already implemented: `fact_state.join` reserves
its result arrays, and `lifecycle_runtime.resource` caches completed per-type
answers. Narrowed-node borrowing has also received substantial fixes. Refresh
the profile before attributing the older costs to the present code.

Keep the COW latency question open, as requested. Static site counts cannot
establish predictable runtime costs: a single hot detach may dominate thousands
of bounded stores. Continue reporting logical copies independently of physical
sharing, moves, placement and allocator traffic. Removing COW should follow
proof-backed replacements, not precede them.

## Correctness and proof boundaries

The finite fact domain is much more substantial than the roadmap's opening
description of an interval checker. It includes difference paths, disequalities,
weighted candidates, mutation-aware routes, branch joins and bounded loop
search. The recent cutoff repair is important: exhausting a budget yields
unknown, not an induction certificate. Preserve that discipline.

Three pieces deserve priority over additional clever entailment rules:

1. **Actual unsafe dependency provenance.** `semantic/unsafe_audit.py` explicitly
   lists candidate checks in an assumption-bearing function. It does not trace
   which discharged obligations consumed an assumption. Track origins through
   transfer, invalidation, joins and call contracts; preserve the audit before
   proof erasure and pruning. Conservative dependencies are acceptable, but
   unrelated checks must not be presented as demonstrated consumers.
2. **One storage decision, several consumers.** Allocation contracts, copy
   policy, borrow legality and lowering already share some storage proofs. Finish
   that contract for the supported shapes instead of giving each consumer a
   slightly different collection of expression exceptions. Logical lifecycle
   work must remain visible even when its bytes can borrow.
3. **A targeted boundary matrix.** Test aliasing, sibling fields, selector
   evaluation, defaults, call argument order, imported helpers, captures,
   control-flow joins and owner replacement in combinations. Recent repairs
   show why individually supported operations can fail when composed. Retain
   explicit expected results and rejection checks, not only compiler agreement.

Unknown proof results need useful explanations: unsupported fragment,
invalidated identity, missing callee contract, or exhausted search budget.
Instrument these reasons and query counts before growing the solver. A general
solver rewrite is not needed to obtain useful uniformity.

Resource exhaustion is a genuine unsettled limit on the no-hidden-exit goal.
Heap growth, recursion, failure reporting and cleanup need a coherent capacity
model. `semantic/resource_exhaustion.md` correctly treats this as open. Allocation
placement or termination alone cannot establish sufficient memory or stack.
Do not silently choose a failure effect or promise full trap freedom here.
Explicit `$runtime_assert` and `$prototype` checks are separate, opted-in paths.

## Capability: distinguish implemented slices from the intended language

Small executable hosted probes and native acceptance checks confirm that
inferred user generic functions and array-literal spread work. The same probes
do not establish full generic types or all spreading forms. Inspection and
focused rejection probes leave these significant limits:

| Area | Useful current slice | Remaining limitation and consequence |
| --- | --- | --- |
| Generics | Named generic functions instantiate concrete bodies; generic type aliases and effect-row inference exist. | Explicit generic function arguments and user generic object/container types remain incomplete. Generic proof functions and first-class generic function values are rejected. Containers cannot yet migrate wholesale into ordinary libraries. |
| Callables | Function values, callbacks and lambda-lifted nonescaping read captures exist. | Escaping captures and captured writes need environment ownership. Closures are already a Phase 2 item; they should not be an implicit prerequisite to closing every Phase 1 lifetime case. |
| Proofs | Checked, erased direct proof statements and the finite fact system work. | This is a deliberately restricted terminating proof subset, not general pure compile-time evaluation. Dependent aggregate relationships remain incomplete. |
| Storage | Scoped arenas, loans, frame scalar aggregates and many partial resource transfers exist. | Owner-directed promotion, general small scratch placement, mutable/repeated selector lifetimes and some resource operations remain conservative or unsupported. Valid conservative rejection is different from a miscompilation. |
| Types and numerics | Structural/nominal records, integer refinements, big integers, rational/fixed libraries and dimensional types are useful. | Primitive minting such as `type of int64` is still pending. Abstract `int` locals can become big integers, while ordinary signatures still impose a word ABI in important cases. IEEE arithmetic, shapes, broadcasting and engineering math remain far from the front-page ambition. |
| Compile-time programming | Type expressions and specialized generic bodies do substantial static work. | Reflection, derived object construction and general effect-checked evaluation are incomplete; the compiler still owns many container/layout/helper conventions. |
| Errors and invocation | Union errors, forwarding, CLI/test/debug/install paths exist. | Transformed propagation and some call/iterator forms remain incomplete. Several pending constructs report implementation-level diagnostics rather than a clear supported-feature boundary. |
| Reach and tooling | Multiple µDewy backends and direct object writers exist; a verified native package is installable. | The installer is Linux x86-64 only, system libraries remain Linux-oriented, the complete prelude is not portable, and there is no semantic language server or package ecosystem yet. Backend existence is not full language/host support. |

Keep the later numerics, portability and concurrency phases. Pull forward only
the smallest already-designed generic/reflection slice that demonstrably
removes compiler special cases. A good first customer is one library abstraction
with paired ownership/effect tests; replacing every builtin container at once
would exchange the current maintenance burden for a migration burden.

The large checkers and lowerers are maintenance risks, but line-count splitting
alone will not help. Extract policies with real inputs/outputs: call binding,
selected routes, storage ownership, representation and obligation discharge.
Keep the Python oracle independently implemented. Share specifications,
fixtures and format definitions; do not generate both checking algorithms from
one implementation and call the resulting agreement independent evidence.

## Feedback, certification and documentation

`build_program_driver` already shares its driver once per pytest worker and
shares an immutable checked prelude. The next improvement is an explicitly
identified driver artifact across appropriate test groups/workers, not another
per-case cache. Bind it to source, library, target and options; keep independent
hosted construction in the certification tier. User-program full builds must
still recheck user source. Improving test infrastructure does not require an
incremental compiler or resident daemon.

Proposed validation tiers:

- **Per batch:** relevant hosted semantic tests, paired expected-result cases,
  small ownership/allocation/scaling kernels, then a coherent commit.
- **Integration checkpoint:** frozen source, independently hosted-built seed,
  complete paired manifest, native fixed point and surrounding tests.
- **Scheduled/release certification:** full pytest, cache corrupt/stale/cold
  checks, installer/debug/target checks and reproducible packaging for that SHA.

Do not skip required checks because they are slow; make their setup reusable and
their scope explicit. Add machine-readable timing/work budgets for the small
program, representative module and full compiler. Large suites are integration
evidence, not the inner optimization loop.

The release workflow currently runs independently of `tests.yml`. It verifies
three native generations plus `check_native.sh`, then publishes. It does not
wait for full pytest or the complete differential manifest. Gate publication on
certification of the same source revision; fixed-point determinism cannot
substitute for expected-result tests. Keep hosted recovery explicit.

Documentation is currently an unreliable capability index. Examples:

- `status.md` says user generic functions and array-literal spread are missing,
  while both acceptance probes succeed. Its “Completely unimplemented” list
  still includes dictionaries, matching and the native bootstrap.
- `IMPLEMENTATION.md` opens its parity section with older blockers that later
  checkpoint prose supersedes. Readers have to reconstruct current status.
- The roadmap still lists join reservation and resource memoization as future
  optimizations; both are present.
- Fixed-width rollover is explicit in the implementation status, while
  `no_traps.md` describes explicit fixed-width arithmetic as carrying overflow
  alternatives more broadly. Reconcile the normative wording without changing
  established arithmetic semantics during an optimization pass.

Maintain one concise current capability/certification table with links to
fixtures and design notes. Keep historical checkpoints in appendices. Record
semantic support, cost guarantees, backend coverage and certification separately.

## Proposed roadmap changes

| Order | Deliverable | Completion evidence |
| --- | --- | --- |
| 1 | Freeze the remaining Phase 1 closure matrix: supported ownership operations, shared storage decisions, unsafe provenance, strict-source adoption/report parity and final integration. Explicitly assign closure-dependent captures and genuinely open resource designs to their existing later/design tracks. | Every row has an acceptance/rejection example and an implementation/parity status. No claim that conservative unsupported cases are fully implemented. |
| 2 | Improve the feedback path and release certification while closing those rows. | A bounded local gate, identified shared test-driver artifacts, and publication gated by checks for the exact revision. |
| 3 | Resume the sustained throughput campaign within the remaining Phase 1 work, before broad feature expansion. Do not wait for every compiler module to adopt strict mode. Prioritize allocation elimination and redundant analysis; improve direct-generated compiler code alongside measured frontend work. | Uncached user-source full builds, separate executing-compiler provenance, under 30 seconds minimum / under 10 seconds stretch, plus memory, allocation and scaling budgets. No C required for the direct acceptance row. |
| 4 | Start a narrow Phase 2 generic/reflection/library customer after Phase 1 closure, once its proof/effect prerequisites are stable. | One abstraction genuinely moves out of checker special cases, with ordinary Dewy contracts and both compiler implementations. Expand from that evidence. |
| 5 | Continue closures/error completeness, then engineering numerics, portability and ecosystem work in the existing order. | Small complete examples for each milestone, not parsing-only support or frontend claims inferred from backend intrinsics. |

This changes the sequence of work, not the scope of the approved Phase 1 request.
Unsupported cases stay recorded; declaring a milestone complete requires its
agreed closure evidence. Do not make “the full ideal solver”, “every possible
lifetime shape” or “all resource failure designs settled” hidden exit criteria.
Those are continuing language goals, and a finite roadmap needs explicit
implementation boundaries.

Avoid broad parser rewrites, a new optimizing backend dependency, universal
arenas, speculative parallel checking and premature retirement of Python.
First remove redundant work. Parallel per-function analysis becomes attractive
after mutable graph ownership and dependencies are explicit; it is not a cure
for copying the same state on several cores.

## Follow-up: semantic composition and local representations (2026-09-30)

This follow-up emphasizes blind spots beyond the existing feature and performance
roadmap. Source baseline: `7dcf76726b237187f68ab18bf06e9c3cf56cfa63`. A frozen
archive isolated the later probes from simultaneous development. The audit did
not edit compiler sources. Small serial probes ran at low priority with process
limits while other builds were active; no full native rebuild or performance
campaign was run.

### Evidence and assessment

The targeted baseline passed **80 tests, with one native case deselected, in
9.30 seconds**. It covered scalar semantics, minted types, integer widths, effect
rows, relational closure and Unicode graphemes. Runtime counterexamples below
used the hosted compiler through µDewy to x86-64. Native counterparts were inspected
where noted; source inspection is not native execution evidence. Four subsequent
small probes generated lowered output/diagnostics for call specialization only.
These results do not certify the whole revision.

The value/place distinction, mutation-aware facts, conservative proof handling,
ownership contracts and independently implemented hosted/native checking remain
strong foundations. The tests and measured performance work are substantial.
The new issues concern how these mechanisms compose, and when an implementation
choice made for a broad type or function needlessly affects a local use.

The release gap in the earlier audit is now addressed: at this baseline,
[`release-native.yml`](../.github/workflows/release-native.yml) gates publication
on successful tests for the packaged revision, with the paired manifest and
native generation checks. This is a workflow-source observation, not a claim
that the auditor ran a fresh complete certification.

### Clarified direction from David

- **Fresh builds:** the long-term model rebuilds projects from scratch without
  incremental compilation or persistent compiler caches. The checked-prelude
  cache is transitional, not a permanent exception. Within-invocation work reuse
  and test-driver artifacts are separate from user-build caching.
- **Local specialization:** private representations and call protocols should
  follow proven local uses, approaching what a programmer would efficiently
  write for that problem. A broad semantic type need not impose its most general
  physical representation everywhere. Conversion belongs at boundaries that
  actually require generality.
- **Library validators:** favor ordinary library-defined compile-time validation.
  Ideally guarantees trace back to language/type-system checking, but a narrow
  documented trusted boundary is a reasonable provisional default where complete
  proofs are disproportionately difficult. The exact mechanism is undecided and
  should be reevaluated with use; see [idiomatic facts](semantic/idiomatic_facts.md#library-validation-default-2026-09-30).
- **General compile-time execution:** trust the programmer. It may run indefinitely
  or exhaust resources; mandatory termination proofs or execution budgets are not
  selected language requirements. Useful diagnostics and cancellation remain
  tooling goals. Automatic proof-search budgets still yield unknown, never proof.

These clarifications adjust recommendations, not the recorded behavior of the
audited implementation. The lifecycle payload question below remains open.

### 1. Spelling-dependent semantics and observable interpolation rewrites

The hosted lowerer reads `$no_prelude` with a regular expression over raw source
in [`lower.py`](backend/udewy/lower.py), despite the checker already having parsed
the directive. This program exits `1`:

```dewy
$no_prelude = true
shift=(x:uint64 n:uint64):>uint64=>x << n
main=():>int64=>shift(1 64) transmute int64
```

Changing only the directive to `$no_prelude = # comment`, with `true` on the next
line, makes it exit `0`. Both parse as the same directive. Carry parsed metadata
into lowering; a raw-shift compatibility mode must not depend on comment layout.

The interpolation rewrite in [`semantic/check.py`](semantic/check.py)
(`_tcr_output_call`) and its [native counterpart](bootstrap/semantic/check.dewy)
recognizes the names `print`/`printl` plus a generic signature, rather than the
resolved prelude binding. This probe prints `A2B` and exits zero; the shadowing
function is bypassed:

```dewy
let count:int64=0
let printl=<T>(x:T):>void=>{count+=1}
main=():>int64=>{printl"A{2}B" return count}
```

There is an independent effect-order problem:

```dewy
side=():>int64=>{printl"SIDE" return 2}
main=():>int64=>{printl"A{side()}B" return 0}
```

Direct interpolation outputs `ASIDE\n2B\n`. Replacing the call with
`let s="A{side()}B" printl(s)` outputs `SIDE\nA2B\n`. The
[string reference](../site/reference/src/strings.md#interpolation) describes the
streaming/materialization choice as unobservable.

**Required direction:** recognize checked binding/intrinsic identity and preserve
argument evaluation and effects. Add transformation cases for comments, shadowing,
aliases, helper extraction and materialization. Moving operations into libraries
does not resolve spelling-based compiler recognition by itself.

### 2. Executable hosted caches are a temporary trust defect

[`_parse_module`](semantic/check.py) and the
[checked-prelude loader](semantic/modules.py) call `pickle.loads` on project-relative
cache files before validation. A benign isolated pickle invoked a function that
printed an audit marker during loading, before normal parsing recovered and wrote
a valid entry. A digest in the filename validates freshness, not producer trust;
validation after deserialization cannot prevent that execution.

This concerns the hosted pickle paths, not the native codec. With persistent
build caching outside the intended design, removal or disabling is a valid
resolution. Do not infer a need for a permanent cache architecture. While that
transitional path remains usable, it still needs a trustworthy loading boundary.

### 3. Record-family layout creates nonlocal costs and storage cycles

[`_object_layout`](backend/udewy/lowering_objects.py) reserves a parent's largest
descendant; [native layouts](bootstrap/backend/udewy/layouts.dewy) use the same
policy. This was an explicit September 2 decision recorded in `status.md`.
Hosted layout queries measured a root with one `int64` field at 16 bytes, 24 bytes
after adding an unused child with one extra field, and 144 bytes after adding a
child with sixteen extra fields.

This finite value typechecks but hosted code generation raises `RecursionError`:

```dewy
$no_prelude=true
Root=type of [x:int64]
Child=type of Root & [parent:Root]
main=():>int64=>{let c=Child[1 Root[2]] return c.parent.x}
```

The native source detects the layout cycle and returns pending indirection;
that path was not executed here. Whole-program compilation permits a closed-world
representation, but does not eliminate its nonlocal footprint or the need for
indirection in recursive polymorphic storage.

**Design question:** distinguish exact concrete storage from slots that can
actually hold arbitrary descendants. Sealed families or boxed polymorphic forms
are options, not decisions. Exact-brand local specialization can remove the
general form from many uses while retaining it at real boundaries. Fixing only
the recursion diagnostic would leave that representation question unresolved.

### 4. Aggregate arrays need explicit dense-storage criteria

[`_array_element_layout`](backend/udewy/lowering_arrays.py) and
[native element layouts](bootstrap/backend/udewy/layouts.dewy) store fixed-width
scalars densely but use handles/cell pointers for records, optionals and general
unions. An array of two-integer records is currently an array of handles, rather
than contiguous 16-byte records. Lifetime/frame optimizations may avoid separate
heap allocations; the indirection still exists.

Copy elimination and allocator improvements alone do not remove that form.
Phase 3's contiguous CPU/GPU goals need explicit aggregate-element stride,
representation, lifetime, mutation, borrowing and foreign/device-buffer criteria.
Use homogeneous particle, complex-number and optional-number workloads, plus
heterogeneous counterexamples. No workload-level slowdown percentage was measured.

### 5. Elidable lifecycle hooks can change payload values

Observable hook effects and variable invocation counts were deliberately approved.
The open question is what value an elidable copy/move must preserve. This probe
prints `1 101\n`:

```dewy
Token=type of [id:int64
$__drop__ release=():>void=>{}
$__move__ relocate=():>Token=>Token[id+100]]
fresh=():>Token=>Token[1]
named=():>Token=>{let value=Token[1] return value}
main=():>int64=>{let a=fresh() let b=named() printl"{a.id} {b.id}" return 0}
```

This follows current rules; it is not presented as a miscompilation. Introducing
a local changes payload data, not just diagnostic hook counts. Existing lifecycle
tests also intentionally modify payload fields in move hooks. Decide whether
elidable hooks have a checked, trusted or conventional value-preservation law,
or distinguish semantic operations from relocation. Record that answer before
broader specialization assumes it. See the open question added to
[the lifecycle design](PHASE1_DESIGN_PROPOSALS.md#observable-effects-and-elision).

### 6. Construction authority is a present library concern

The [invariant design notes](semantic/idiomatic_facts.md) already identify
construction authority; this is an underprioritized known question with a concrete
current consequence. This compiles and exits `42`:

```dewy
main=():>int64=>{
    let invalid:bigint=[sign=1 limbs=[0]]
    return if invalid =? 0 0 else 42
}
```

The [bigint library](../library/bigint.dewy) relies on canonical base-2^32 limbs,
but ordinary typed construction can violate that convention. The field type also
does not restrict every `uint64` limb to 32 bits. This is not a claim that every
malformed value traps.

A compile-time validator can reject this known literal. For general inputs the
provisional library-validator strategy must establish or explicitly trust the
invariant and connect it to every relevant constructor/conversion/mutation route.
Copying and supported reflection/generated construction need coverage too.
Success may establish a predicate; deriving other facts needs checked implications
or the documented trust boundary. The first Phase 2 library customer should make
this end-to-end mechanism concrete, without waiting for arbitrary invariant proofs.

### 7. Independent library boundary expectations are needed now

Compiler parity shares runtime algorithms. Two executed failures demonstrate why
small independent expected-result cases should precede the larger numerical phase:

- **Fixed-point minimum divided by itself produces zero.** With
  `let a:fixed=[raw=(-9223372036854775808)]`, exclude `a.raw=?0` and compute
  `let result=a/a`. The observed `result.raw` is `0`; the representable correct
  result is one, raw `4294967296`. In [`_fixed_div`](../library/fixed.dewy), the
  wrapped minimum absolute magnitude incorrectly selects the zero-result path.
- **Interior NUL changes a filesystem target.** With an existing `intended-file`,
  `read_text("intended-file\0ignored")` reads that file. The probe used an actual
  NUL in the literal, shown escaped here. [`_c_path_into`](../library/linux/files.dewy)
  copies it without rejection, so the kernel consumes only the prefix.

Source inspection additionally found that [`capture`](../library/linux/process.dewy)
returns after failure to create its second pipe without closing the first pipe's
descriptors. That failure was not injected at runtime.

The [numerical stress-test design](semantic/numerical_stress_test.md) already
proposes Python integer/Fraction oracles. Pull a small subset forward: representable
endpoints, rounding, canonical forms and exact identities. Add OS encoding and
partial resource-acquisition cases with independent expected outcomes. This is a
change in sequencing, not a claim that independent oracles were never planned.

### 8. Generic growth needs a useful failure mode, not a mandatory language budget

This hosted probe raises `RecursionError` during checking:

```dewy
$no_prelude=true
let f=<T>(x:T):>int64=>f([x])
main=():>int64=>f(1)
```

[Generic instantiation](semantic/check.py) registers an instance before checking
its body, handling same-type recursion but not an endless sequence of larger
instances. The initial recommendation to mandate instance/work budgets is
superseded by David's programmer-trust clarification. Track this as diagnostic,
cancellation and tooling recovery work. It is not a requirement that the language
accept infinite specialization or prove all compile-time programs terminate.

### Deeper follow-up: retain local information through lowering

A newly reproduced example shows a whole-function decision affecting unchanged
direct calls. This program compiles under `$explicit_copies`:

```dewy
$explicit_copies
Pack:type=[text:string values:array<int64>]
make=():>Pack=>Pack['owned' [2]]
change=(p:Pack):>int64=>{
    p.values.push(40)
    return if p.values.length>?1 p.values[0]+p.values[1] else 0
}
main=():>int64=>{let p=make() return change(p)}
```

Adding only `let callback=@change` inside `main` makes it fail with **`unproven
copy`**, even though the callback is never called. Hosted lowering collects
functions used as values and excludes them from private ownership-input protocols
in [`lower.py`](backend/udewy/lower.py). The corresponding exclusions are present
in [native borrowing](bootstrap/backend/udewy/borrowing.dewy). Only the hosted
acceptance/diagnostic was executed here.

A simpler scalar-record probe confirms that taking the function value changes
the ABI: the direct-only form prepares the independent argument at the call site;
the address-taken form copies it on callee entry. That simpler probe does not
demonstrate a higher total copy count. The ownership-bearing example above shows
the stronger consequence for copy-policy acceptance.

Retain a private direct-call entry and a general function-value entry/adapter
where required. A coherent indirect-call ABI and function identity need not force
every statically known direct call through the same conservative ownership path.

The project already has useful local specialization:

- [`_scalar_getter_projection` and `_borrowed_getter_projection`](backend/udewy/lowering_objects.py)
  generate private variants for demanded fields or stable borrowed results.
- [Array classification](backend/udewy/lowering_arrays.py) and
  [shared placement proofs](semantic/placement.py) select stack/static storage
  when uses permit it.
- Direct ownership inputs, last-use moves and caller-provided destinations
  preserve information beyond a broad semantic type.

Extend these mechanisms consistently. Other broad decisions visible in source
include alias-group-wide array representations, binding-wide bigint promotion
after one large assignment, and prepared storage for some union alternatives.
The last point is shape-dependent: many arena-backed record alternatives already
allocate only the active form; fixed-array and other prepared trees remain.
These observations were not separately benchmarked.

The next design step is shared representation planning before raw loads/stores:
reachable concrete alternatives, ownership/lifetime, demanded fields/results,
physical shape and required materialization/conversion boundaries. Copy/drop,
equality, calls and allocation contracts should consume those decisions. Logical
narrowing must stay distinct from physical storage: the existing
[`_stored_union_members`](backend/udewy/lowering_optionals.py) distinction is
necessary for correctness and must survive this work.

Stable addresses, live aliases, heterogeneous values and unknown callees impose
real generality. Put that obligation at the relevant boundary. For other regions,
keep exact records compact, field-only values scalar, homogeneous aggregates dense
and known calls specialized. Share variants by representation/ownership/result
demand and callee summaries to protect fresh-build speed; unrestricted per-call
cloning could create a new compilation and code-size problem.

### Work ordering and acceptance

| Work | Next evidence |
| --- | --- |
| Concrete semantic and library defects | Paired expected-result/rejection cases for spelling, binding identity and effect order; independent arithmetic/OS boundary expectations; remove or disable executable cache loading while it remains. |
| Local representations and call protocols | An unchanged direct call retains its ownership path after address-taking; unused descendants do not inflate exact locals; field-only consumers avoid full-record copies; dense homogeneous records have the intended stride. Include cases where generality is required. |
| Lifecycle contract | An explicit decision on payload preservation and trust/proof obligations, preserving the already-approved effect/elision rules until changed deliberately. |
| Library validators | One invariant-bearing customer covers known and runtime input, construction/conversion/mutation, copied evidence and exported facts, with checked/trusted provenance visible. |
| Compile-time tooling | Useful instantiation diagnostics and cancellation/recovery without turning automatic proof budgets into mandatory limits on general user execution. |

Measure behavior, allocation/copy/dispatch work, emitted size and compilation cost
separately. Keep these as focused additions to the existing correctness and
throughput work, with deeper representation/library support staged in the roadmap.
No full native certification, sustained fuzzing or cross-platform/performance claim
is made by this follow-up.

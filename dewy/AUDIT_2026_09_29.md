# Compiler audit and proposed roadmap adjustments

Reviewed source at `a202b734`, after the parameter-based effect worklist
checkpoint. This is an architectural review with source inspection, focused
capability probes and an independent hosted seed build. It is not a line-by-line
verification of every implementation or a fresh green full-suite certification.
Recommendations below are proposals; they do not redefine the language or mark
Phase 1 complete.

## Assessment

The direction is sound: retain value semantics, checked facts, explicit places,
ordinary Dewy libraries, the Dewy/µDewy split and the dependency-free Python
reference. Native self-hosting, differential checks, deterministic cleanup and
the binary output path are substantial foundations. Do not replace them with a
new compiler architecture merely because the current implementation is slow.

The largest obstacle is now the cost of advancing those foundations. Too much
work still creates, copies and reinterprets small aggregate objects; multiple
consumers rediscover related facts; broad validation is expensive; and current
capabilities are mixed with historical plans in the documentation. Continuing
one source shape at a time indefinitely would make Phase 1 an expanding queue
rather than a milestone.

I recommend a bounded correctness closure with a focused throughput campaign
inside the remaining Phase 1 work, then a small Phase 2 library-enabling slice. These are
engineering changes to the roadmap's execution, not a change to Dewy's goals.

## Performance: remove work before tuning how it runs

### Allocation frequency is at least as important as copied bytes

The historical profile's 402 million allocations would require 40.2 million
allocations per second to fit a ten-second *whole build*. That permits only
25 ns per allocation before parsing, checking, lowering or backend work. At
3.4 GHz that is roughly 85 cycles. It is not a lower bound on compiler time:
many of those allocations are unnecessary. It demonstrates why making one
allocator call a little cheaper cannot deliver the intended result.

The source is about 3 MB, while aggregate traffic is tens of GB. Allocation
counters are not literal DRAM bandwidth: they include recycled blocks, size
classes and repeated temporary storage. Nevertheless, this disparity justifies
eliminating whole classes of representation work. Measure visit counts, state
entries, allocations, detachments and bytes alongside wall time. Do not infer
an achievable compiler time from source bytes divided by peak memory bandwidth.

Specific remaining candidates:

| Candidate | Current evidence | Proposed next action |
| --- | --- | --- |
| Empty aggregate storage | `lower.array_memory` avoids an empty data buffer but still constructs a private descriptor. The older profile attributed 73.7 M descriptor allocations to `[]`. | Introduce an immutable empty representation behind the existing value interface, materializing a private owner on mutation. Check places, reserve, cleanup, nested fields and allocator ownership; a shared descriptor must never become writable. |
| Small temporary collections | Parser candidates, child worklists, effect paths and statement prefixes frequently allocate short arrays. Fixed scalar frame placement already exists; general growable scratch lists are a different case. | Use bounded inline storage with a measured spill path for proven nonescaping scratch owners. Cover both compilers' semantics without requiring equal storage costs. |
| Mutable analysis snapshots | Facts and branch states still own arrays, records and dictionaries. COW avoids some immediate copying but can defer a large detach. | Profile the remaining state operations, use one owner for mutable construction, borrow immutable inputs, and transfer completed results. Prefer flat IDs and compact entries where they remove ownership trees. Do not globally replace value semantics with aliases. |
| Repeated analysis discovery | Local places, lifecycle handling, place contracts, bounds preparation, public effects and lowering consume overlapping graph/route information. | Inventory the repeated traversals and share a revision-bound analysis context where semantics match. Propagate changed summaries by dependency; retain distinct modes when they differ, such as raw exposure and `value_casts_escape`. |
| Intermediate representations | Dewy emits µDewy tokens which a parser port records as backend operations; direct object writers still consume generated assembly strings. | Remove one measured intermediate at a time, driving the existing operation protocol directly. Preserve text/reference routes and target/ABI checks. Do not add another independently maintained IR merely to bypass one format. |
| Executing compiler code | The direct backend already has local register allocation and an expression register cache. Its generated compiler has historically been slower than a C-built one. | Profile generated compiler instructions/calls/spills, then improve the direct backend on representative kernels. Measure emission time and runtime throughput separately. An optimization that slows compilation but improves subsequent compiler generations may still be worthwhile. |

Two older recommendations are already implemented: `fact_state.join` reserves
its result arrays, and `lifecycle_runtime.resource` caches completed per-type
answers. Narrowed-node borrowing has also received substantial fixes. Refresh
the profile before attributing the older costs to the present code.

Keep the COW latency question open, as requested. Static site counts cannot
establish predictable runtime costs: a single hot detach may dominate thousands
of bounded stores. Continue reporting logical copies independently of physical
sharing, moves, placement and allocator traffic. Removing COW should follow
proof-backed replacements, not precede them.

## Correctness and proof boundaries

The finite fact domain is much more substantial than the roadmap's opening
description of an interval checker. It includes difference paths, disequalities,
weighted candidates, mutation-aware routes, branch joins and bounded loop
search. The recent cutoff repair is important: exhausting a budget yields
unknown, not an induction certificate. Preserve that discipline.

Three pieces deserve priority over additional clever entailment rules:

1. **Actual unsafe dependency provenance.** `semantic/unsafe_audit.py` explicitly
   lists candidate checks in an assumption-bearing function. It does not trace
   which discharged obligations consumed an assumption. Track origins through
   transfer, invalidation, joins and call contracts; preserve the audit before
   proof erasure and pruning. Conservative dependencies are acceptable, but
   unrelated checks must not be presented as demonstrated consumers.
2. **One storage decision, several consumers.** Allocation contracts, copy
   policy, borrow legality and lowering already share some storage proofs. Finish
   that contract for the supported shapes instead of giving each consumer a
   slightly different collection of expression exceptions. Logical lifecycle
   work must remain visible even when its bytes can borrow.
3. **A targeted boundary matrix.** Test aliasing, sibling fields, selector
   evaluation, defaults, call argument order, imported helpers, captures,
   control-flow joins and owner replacement in combinations. Recent repairs
   show why individually supported operations can fail when composed. Retain
   explicit expected results and rejection checks, not only compiler agreement.

Unknown proof results need useful explanations: unsupported fragment,
invalidated identity, missing callee contract, or exhausted search budget.
Instrument these reasons and query counts before growing the solver. A general
solver rewrite is not needed to obtain useful uniformity.

Resource exhaustion is a genuine unsettled limit on the no-hidden-exit goal.
Heap growth, recursion, failure reporting and cleanup need a coherent capacity
model. `semantic/resource_exhaustion.md` correctly treats this as open. Allocation
placement or termination alone cannot establish sufficient memory or stack.
Do not silently choose a failure effect or promise full trap freedom here.
Explicit `$runtime_assert` and `$prototype` checks are separate, opted-in paths.

## Capability: distinguish implemented slices from the intended language

Small executable hosted probes and native acceptance checks confirm that
inferred user generic functions and array-literal spread work. The same probes
do not establish full generic types or all spreading forms. Inspection and
focused rejection probes leave these significant limits:

| Area | Useful current slice | Remaining limitation and consequence |
| --- | --- | --- |
| Generics | Named generic functions instantiate concrete bodies; generic type aliases and effect-row inference exist. | Explicit generic function arguments and user generic object/container types remain incomplete. Generic proof functions and first-class generic function values are rejected. Containers cannot yet migrate wholesale into ordinary libraries. |
| Callables | Function values, callbacks and lambda-lifted nonescaping read captures exist. | Escaping captures and captured writes need environment ownership. Closures are already a Phase 2 item; they should not be an implicit prerequisite to closing every Phase 1 lifetime case. |
| Proofs | Checked, erased direct proof statements and the finite fact system work. | This is a deliberately restricted terminating proof subset, not general pure compile-time evaluation. Dependent aggregate relationships remain incomplete. |
| Storage | Scoped arenas, loans, frame scalar aggregates and many partial resource transfers exist. | Owner-directed promotion, general small scratch placement, mutable/repeated selector lifetimes and some resource operations remain conservative or unsupported. Valid conservative rejection is different from a miscompilation. |
| Types and numerics | Structural/nominal records, integer refinements, big integers, rational/fixed libraries and dimensional types are useful. | Primitive minting such as `type of int64` is still pending. Abstract `int` locals can become big integers, while ordinary signatures still impose a word ABI in important cases. IEEE arithmetic, shapes, broadcasting and engineering math remain far from the front-page ambition. |
| Compile-time programming | Type expressions and specialized generic bodies do substantial static work. | Reflection, derived object construction and general effect-checked evaluation are incomplete; the compiler still owns many container/layout/helper conventions. |
| Errors and invocation | Union errors, forwarding, CLI/test/debug/install paths exist. | Transformed propagation and some call/iterator forms remain incomplete. Several pending constructs report implementation-level diagnostics rather than a clear supported-feature boundary. |
| Reach and tooling | Multiple µDewy backends and direct object writers exist; a verified native package is installable. | The installer is Linux x86-64 only, system libraries remain Linux-oriented, the complete prelude is not portable, and there is no semantic language server or package ecosystem yet. Backend existence is not full language/host support. |

Keep the later numerics, portability and concurrency phases. Pull forward only
the smallest already-designed generic/reflection slice that demonstrably
removes compiler special cases. A good first customer is one library abstraction
with paired ownership/effect tests; replacing every builtin container at once
would exchange the current maintenance burden for a migration burden.

The large checkers and lowerers are maintenance risks, but line-count splitting
alone will not help. Extract policies with real inputs/outputs: call binding,
selected routes, storage ownership, representation and obligation discharge.
Keep the Python oracle independently implemented. Share specifications,
fixtures and format definitions; do not generate both checking algorithms from
one implementation and call the resulting agreement independent evidence.

## Feedback, certification and documentation

`build_program_driver` already shares its driver once per pytest worker and
shares an immutable checked prelude. The next improvement is an explicitly
identified driver artifact across appropriate test groups/workers, not another
per-case cache. Bind it to source, library, target and options; keep independent
hosted construction in the certification tier. User-program full builds must
still recheck user source. Improving test infrastructure does not require an
incremental compiler or resident daemon.

Proposed validation tiers:

- **Per batch:** relevant hosted semantic tests, paired expected-result cases,
  small ownership/allocation/scaling kernels, then a coherent commit.
- **Integration checkpoint:** frozen source, independently hosted-built seed,
  complete paired manifest, native fixed point and surrounding tests.
- **Scheduled/release certification:** full pytest, cache corrupt/stale/cold
  checks, installer/debug/target checks and reproducible packaging for that SHA.

Do not skip required checks because they are slow; make their setup reusable and
their scope explicit. Add machine-readable timing/work budgets for the small
program, representative module and full compiler. Large suites are integration
evidence, not the inner optimization loop.

The release workflow currently runs independently of `tests.yml`. It verifies
three native generations plus `check_native.sh`, then publishes. It does not
wait for full pytest or the complete differential manifest. Gate publication on
certification of the same source revision; fixed-point determinism cannot
substitute for expected-result tests. Keep hosted recovery explicit.

Documentation is currently an unreliable capability index. Examples:

- `status.md` says user generic functions and array-literal spread are missing,
  while both acceptance probes succeed. Its “Completely unimplemented” list
  still includes dictionaries, matching and the native bootstrap.
- `IMPLEMENTATION.md` opens its parity section with older blockers that later
  checkpoint prose supersedes. Readers have to reconstruct current status.
- The roadmap still lists join reservation and resource memoization as future
  optimizations; both are present.
- Fixed-width rollover is explicit in the implementation status, while
  `no_traps.md` describes explicit fixed-width arithmetic as carrying overflow
  alternatives more broadly. Reconcile the normative wording without changing
  established arithmetic semantics during an optimization pass.

Maintain one concise current capability/certification table with links to
fixtures and design notes. Keep historical checkpoints in appendices. Record
semantic support, cost guarantees, backend coverage and certification separately.

## Proposed roadmap changes

| Order | Deliverable | Completion evidence |
| --- | --- | --- |
| 1 | Freeze the remaining Phase 1 closure matrix: supported ownership operations, shared storage decisions, unsafe provenance, strict-source adoption/report parity and final integration. Explicitly assign closure-dependent captures and genuinely open resource designs to their existing later/design tracks. | Every row has an acceptance/rejection example and an implementation/parity status. No claim that conservative unsupported cases are fully implemented. |
| 2 | Improve the feedback path and release certification while closing those rows. | A bounded local gate, identified shared test-driver artifacts, and publication gated by checks for the exact revision. |
| 3 | Resume the sustained throughput campaign within the remaining Phase 1 work, before broad feature expansion. Do not wait for every compiler module to adopt strict mode. Prioritize allocation elimination and redundant analysis; improve direct-generated compiler code alongside measured frontend work. | Uncached user-source full builds, separate executing-compiler provenance, under 30 seconds minimum / under 10 seconds stretch, plus memory, allocation and scaling budgets. No C required for the direct acceptance row. |
| 4 | Start a narrow Phase 2 generic/reflection/library customer after Phase 1 closure, once its proof/effect prerequisites are stable. | One abstraction genuinely moves out of checker special cases, with ordinary Dewy contracts and both compiler implementations. Expand from that evidence. |
| 5 | Continue closures/error completeness, then engineering numerics, portability and ecosystem work in the existing order. | Small complete examples for each milestone, not parsing-only support or frontend claims inferred from backend intrinsics. |

This changes the sequence of work, not the scope of the approved Phase 1 request.
Unsupported cases stay recorded; declaring a milestone complete requires its
agreed closure evidence. Do not make “the full ideal solver”, “every possible
lifetime shape” or “all resource failure designs settled” hidden exit criteria.
Those are continuing language goals, and a finite roadmap needs explicit
implementation boundaries.

Avoid broad parser rewrites, a new optimizing backend dependency, universal
arenas, speculative parallel checking and premature retirement of Python.
First remove redundant work. Parallel per-function analysis becomes attractive
after mutable graph ownership and dependencies are explicit; it is not a cure
for copying the same state on several cores.

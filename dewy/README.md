This is the Dewy compiler. It targets udewy, which then targets specific backends.

## Focused compiler checks

Run the relevant file or pytest node while iterating:

```sh
tools/certify.sh focused tests/python_misc/test_bootstrap_type_interning.py
```

To build compiler test drivers with a known native compiler, set
`DEWY_TEST_DRIVER_COMPILER=/absolute/path/to/dewy` for that command. Execution
drivers then build directly to machine code; tests of emitted text retain
their backend checks. Hosted oracle calls remain independent. Unset the
variable to use hosted-built drivers. Driver reuse is keyed by inputs and
compiler content; `DEWY_TEST_DRIVER_CACHE=0` disables reuse for measurements.

`certify.sh local` runs the broader non-slow suite; `certify.sh integration`
retains the independent hosted seed, fixed-point, parity and full-suite gates.

## Editor support
[vscode-dewy/](vscode-dewy/) is a VS Code extension (TextMate grammar + language configuration) structured like `udewy/vscode-udewy/`. Its grammar is generated by `vscode-dewy/scripts/generate_grammar.py` from the tokenizer's tables in `parser/t0.py`, and `tests/python_misc/test_dewy_highlighting.py` keeps it in step with the parser. Highlighting is lexical only; once the bootstrap Dewy compiler exists it will be combined with a proper Dewy language server for semantic highlighting, hover types, member listing, go-to-definition, and diagnostics.

## Recording failed compiles
While working on the tokenizer/parser/checker, `mkdir ~/.dewy/failures` once: from then on every `dewy`, `dewy test`, or `dewy analyze` whose compile fails writes one markdown file there (the command, the error or crash traceback, and every source it read, inlined; library files listed by path) to prune by hand and turn into compiler adjustments. `DEWY_FAILURE_LOG=<dir>` records elsewhere, `DEWY_FAILURE_LOG=0` turns it off; nothing is recorded under pytest. See [failure_log.py](failure_log.py).

## Major changes
- target udewy as primary backend. udewy can then target specific backends
    - special backends like universal shell, etc. can still be directly targeted by dewy
- brand new lexer/parser designed to keep things cleaner
    - t0 is still perhaps a bit complicated given how many constructs it supports. may consider removing the whole inherit from `Token[Context]`, and just replace it with simple lists of which states can read which tokens
    - uses a bottom up precedence parser. very directly related to the precedence table. similar to pratt parsing with binding power, but bottom up instead of top down.
- much improved type checking process (work in progress). TBD the exact shape/semantics, but the whole mul vs call vs index jux ambiguity is tucked neatly in straightforward ambiguous nodes

# Cleanparse implementation status

This document tracks language features in the cleanparse compiler. Checked items are supported through parsing, semantic analysis, udewy lowering, and emission.

## Current focus

Milestone B is being finished in bootstrap-need order (see Sequencing). B1b (recursive union members via handles, member-route narrowing, general unions with `undefined`) landed 2026-08-27 — see the B1 bullet. B8 and the B6 decode remainder landed 2026-08-27 (`join`, the `array<string>` builder idiom, `bytes as string | undefined`). B5-minimal landed 2026-08-27 (`type of error`, error alternatives, `or_throw`). With B1b, B8/B6-decode and B5-minimal in, the **bootstrap compiler in Dewy can begin — David writes it**; B10a spreading and B4a lambda-lifted local functions landed 2026-08-27; B7a user generic functions landed 2026-08-27; the assistant continues with **B9** (the harness) and the leftovers as the bootstrap surfaces needs (B4b closure records, B10b unpacking, B7 generic locals/values), taking the gaps the bootstrap surfaces as top-priority input. B1b's own leftovers (`match`, runtime-sized locals as union members, `array<Node>` member positions) are listed in the B1 bullet. Previously the next slice was described as **B1b: recursive and runtime-sized union members** — the representation is "handle to storage of the member's representation" with the allocation site pluggable (the process-lifetime arena is the first tier, never baked into the layout), plus the three-member `int64|string|undefined` parameter/result limit. A compiler is a recursive AST of sum types, so this is the single biggest bootstrap blocker; `match` syntax is designed alongside it or deferred in favor of `is?` chains.

After B1b: string building and byte decoding (B8 and the B6 remainder), then error values as union members with a propagation idiom (a minimal B5). At that point the **Dewy-written bootstrap compiler begins, and David writes it himself initially** (tokenizer first); the assistant does not write any of the bootstrap compiler and instead continues with other compiler features (B4 closures, B7 generics, the memory track) while it takes shape, using the gaps the bootstrap work surfaces as the highest-priority input.

## Roadmap

The current focus above is phase 1 of this roadmap. Two named milestones anchor the sequencing: **Milestone A** — every example on the site front page compiles and runs as shown; **Milestone B** — the language is comfortable enough to write a compiler in, without the bootstrap itself being part of this roadmap. A good acceptance test for Milestone B is writing the udewy tokenizer in Dewy: it exercises files, growable arrays, dictionaries, unions with matching, strings, and error handling without committing to the full bootstrap.

### Milestone A — front-page examples

In dependency order; A4 and A5 are long-running and interleave with Milestone B work.

- [x] **A1. First-class interpolated strings** (fixes `functions.dewy`, which now runs as shown on the front page). Interpolated strings materialize into complete runtime string descriptors: part bytes are gathered (string copies, runtime integer digits, `true`/`false` selection), then shared UAX #29 segmentation — factored into `_utf8_segmentation`, also reused by the grapheme-array conversion — rebuilds boundaries over the joined buffer, so clusters spanning part joins stay correct. Functions returning materialized strings use a caller-owned result block sized by a compile-time capacity bound (constant bytes plus multiples of string-argument lengths, composed through direct calls, locals, flows, and slices); module-level results use static storage with constant capacity. `print`/`printl` keep the zero-copy streaming path, and `bool` prints and interpolates. Guarded until later: destination-ABI functions as first-class values or object methods, unbounded returned fields, defaulted string parameters in capacity formulas. Still ahead from the original scope: a user-facing `__string__`/`__as__` conversion protocol for interpolating non-builtin types, and unsigned 64-bit formatting (streaming and materialization both treat integers as signed).
- [x] **A2. Ranges as storable values** (fixes `ranges.dewy`, whose card now runs end to end). Range bindings are compile-time values: iterating or testing membership against a stored range resolves the binding back to its literal during checking, so `window = [0..10)` and `evens = 0,2..100` store, iterate, and answer stepped membership with zero runtime representation — constant-anchored memberships even fold to booleans. Range declarations are elided from lowering entirely. Guarded: reassigning a range binding is rejected (resolution would go stale), only compile-time-constant anchors resolve (inlining runtime anchors at the use site could observe later mutations), and any range value reaching lowering unresolved errors. Still ahead: a runtime range representation for runtime anchors, passing and returning ranges, and compound range arithmetic.
- [x] **A3. Iterator-target unpacking and first dictionaries** (fixes `loops.dewy`, whose card now runs end to end). Dictionary declarations (`ratings = ['star wars' -> 73 ...]`, top-level or local, `let` or implicit) desugar at check time into hidden parallel key and value arrays; the visible binding is compile-time only, like ranges. `loop [key value] in dict` unpacks by desugaring to a lockstep `and` multiiterator over the hidden arrays, reusing the existing machinery end to end. Dictionary literals outside declarations, key lookup, growth, and mutation stay pending on a runtime representation (after phase 1 ownership work); `[a b]` unpacking over plain arrays of arrays reports a clear not-implemented instead of the old mixed-condition error.
- [ ] **A4. Fractional numerics and the unit catalog** (fixes `units.dewy`). Rationals and fixed-point are the primary fraction types — `let a = 1/3` should infer a rational — and both lower naturally onto udewy's integer-only core (integer pairs and scaled integers). Floats remain available when explicitly requested but are deliberately deprioritized; no serious float implementation in this roadmap. Then: base dimensions beyond `Time`, dimension products, powers, and division, the unit catalog, `^`, and enough math library for `cos` and `°` over the chosen representations. **Rationals landed (first slice):** `rational` is the prelude object type `Rational = [numerator:int64 denominator:int64]` from `library/rational.dewy`, kept normalized (positive denominator, coprime parts) by `_rational_make`; the operations are ordinary Dewy functions there, so the compiler adds only routing — `a / b` on integers (`/` now maps to `__truediv__`; `//` stays floor division), decimal literals (`9.8` is exactly `49/5`, `1.25e2` is `125`), `+ - *` `/`, negation, and all comparisons with a rational operand call the prelude (integers promote via `_rational_from_int`), and literal operands fold to normalized parts at check time (`6/(-8)` becomes `_rational_make((-3) 4)`; a literal zero divisor is a compile-time error). `print`/interpolation render `n/d`, or `n` when whole. **Powers:** `^` (right-associative) raises integers and rationals to integer powers — constant integer powers fold (`2^10`), runtime ones call `_int_pow` (`library/math.dewy`, squaring) with the exponent required to be a constant or unsigned so the integer result type is sound, a negative constant exponent yields a rational (`2^(-3)` is `1/8`), and rational bases take any integer exponent through `_rational_pow`; narrow fixed-width operands widen to `int64`, other widths are not yet supported. **Compile-time rationals and the dimension algebra landed:** `ty.RationalLiteralType` is the singleton type of an exact rational; constant expressions over integer and rational singletons fold to `hir.RationalConstant` (never lowered — `const` bindings holding one are elided like ranges, and `let` bindings, call arguments, and interpolation fields materialize the folded value through `_rational_make` at the runtime boundary). Dimensions now divide and raise to powers (`ty.divide_dimensions`/`power_dimension`), the base dimensions `Length Mass Current Temperature Amount Luminosity Angle` join `Time` as builtin type aliases, and every arithmetic/comparison operator combines dimensions in the result type (`+ - =? <?` require equal dimensions — `2kg + 3m` is an error; `* /` multiply/divide them; `^` raises them). `library/units.dewy` is the first catalog: SI base units as `1 transmute (1 * Length)`-style unit constants (canonical scales: nanosecond, metre, kilogram, …), prefixes and derived units (`km cm mm g mg minute hour Hz N Pa J W`) as exact rational scales, so `30m/s`, `9.8(m/s^2)`, `1/2 * mass * velocity^2`, and `energy / J` fold to constants or run as `Rational` arithmetic (products cross-reduce so 10^18 time scales divide out without overflowing int64). Quantities are erased before lowering (`_erase_dimensions` retypes nodes by their number). **Base dimensions are still compiler magic:** `Time Length Mass Current Temperature Amount Luminosity Angle` live in `builtin_type_aliases` (`dewy/semantic/builtins.py`), not in any Dewy file. Decision (2026-08): keep that for now; later the library should mint them itself so domain libraries can add their own — candidate syntax `let SomeBaseUnit = type of unit` (may need more; TBD), with the compiler providing only the minting primitive since the dimension algebra already lives in the type checker. **Filed alongside it (2026-08), to do together once the unit declaration syntax exists:** (a) _display units_ — `QuantityType` gains a display unit (symbol + scale, excluded from type equality) inferred from the unit constant a value was written in (`10kg`, `300ms`), composed through `* / ^` (`km/h`), chosen for `+ - =?` as the operand whose scale is closest to canonical (`4km + 5miles` → km), and used by printing (`4500 J`, `300 ms`) with storage staying canonical; (b) `x as km` — `as` with a unit on the right re-tags the display unit after a dimension check (units are values _and_ types, per the book), leaving `x / km` as the way to get the bare number; (c) _offset units_ such as `degC:type = kelvin - 273.15` — the declaration is expressible, the open question is affine semantics: `20degC` is a temperature _point_ (293.15 K), and points only support `point - point → delta` and `point ± delta → point`, so the type needs a point-vs-delta flavor (like datetime vs duration) or arithmetic on them is silently wrong (`20degC * 2` is 586.3 K). Leaning toward the point/delta split (F# and Boost do it), with the caveat that everyday usage routinely says `degC` for a delta too, so `degC` may end up allowed as both, disambiguated by context — TBD. **Fixed-point and trigonometry landed:** `fixed` is the prelude object type `Fixed = [raw:int64]` (`library/fixed.dewy`), Q32.32 with Dewy-written `+ - * /` (the multiply splits 32-bit halves to avoid a 128-bit intermediate; division is a 32-step shift-subtract), comparisons, negation, and round-to-nearest conversions from integers and rationals; a fixed operand absorbs integer and rational operands, compile-time numbers convert to exact raw constants, and `let x:fixed = 1/3` works through `check_against`. **Floats stay out** (decision 2026-08): udewy has no floating-point arithmetic (only bit-pattern helpers for the extern ABI), so floats would mean soft-float or libm linkage; they return later only as an explicit interop type. **Angles are canonical in turns**, so `45°` is the exact rational `1/8 turn` (`° deg degree(s)`), range reduction for trig is exact, and `rad` is the fixed-point unit with the irrational scale; `cos sin tan` take `(rational * Angle)` or `(fixed * Angle)` and return `fixed` (Taylor series over a quarter turn after exact symmetry folding). Overload dispatch prefers exact (`rational`) parameters over `fixed` ones for compile-time number arguments, and the type system knows the prelude's rational/fixed object types so literals match those parameters. **Time is now canonical in seconds** (SI base units everywhere): `s` is scale 1, `ms`/`us`/`ns` are exact rationals, and `sleep` takes `(rational * Time)`, converting to whole nanoseconds at the syscall boundary — the previous nanosecond canonical made derived SI units 10^-18 scales that no fixed representation could hold. `print`/interpolation render fixed values in decimal (up to nine fractional digits, trailing zeros trimmed). Not yet: `^` on fixed bases, `sqrt` and inverse trig, quantity printing with unit names (interpolation prints the bare canonical number), unit conversion helpers (`x in km`), a parameterizable `fixed<N>`, rationals and fixed-point over big integers (their parts are `int64`), runtime zero divisors (pending error values, B5), rationals inside materialized (returned) interpolated strings, runtime bindings with non-ASCII names (udewy rejects them; constants such as `°` are elided so the catalog is fine), and `rational`/`fixed` as nominal types distinct from structurally identical objects.
- [x] **A5. Liquid refinements MVP** (fixes `refinements.dewy`, whose card now typechecks and runs). Parameterize blocks classify entries syntactically per the design: a one-argument lambda (`i => i >? 0`) or a `?`-comparison on `length` is a refinement condition, anything else is a parameter, so `int< i=>i>?0 >`, `array< length>?0 >` (element left open, supplied on application as `NonEmptyArray<int>`), and mixed `array< int64 length<=?4 >` all work. Refinements are `ty.RefinedType(base, propositions)` and live in annotations only: `check_against` proves each proposition at the binding boundary from compile-time facts (integer constants, exact array/string lengths) with the three outcomes from the design — proven (silent), _refuted_ (`score:Positive = -3`), and _unknown_ (`cannot prove refinement`, explicitly not reported as false, hinting at the runtime-check/`unsafe` routes still ahead) — and the binding then carries the base type plus the facts: minimum lengths feed the checker's `length_bounds`, and the bounds analysis seeds integer intervals and runtime-length lower bounds from refined `Declare` annotations. Lowering erases the wrapper alongside dimensions. Also landed for the card: keyword-less annotated declarations (`score:Positive = 42`) share the `let` path, implicit type aliases (`Positive = int<...>`) prebind like `:type` declarations, and `array<int>` takes the int64 word representation. Still ahead (the full system per the design section): refined parameters and results (call-site obligations, facts inside bodies), proofs from control flow (`if n >? 0 { let p:Positive = n }` — the bounds analysis knows the interval but the checker's proof does not consult it yet), `unsafe` claims and checked proofs, propositions beyond integer-literal comparisons (linear arithmetic, relations between parameters and results), value refinements on non-integer bases, and stacked parameterization diagnostics.

### Milestone B — comfortable-to-bootstrap feature set

Ordered by how much each item builds on the previous ones.

- [ ] **B1. General tagged unions and `match`.** A compiler is one large AST of sum types; single-payload `T | undefined` is not enough. Highest-value language feature for bootstrap ergonomics. Done so far: local union bindings with word-sized members (fixed ints, bool, strings/graphemes, `undefined`) lower as tag-and-payload cells sharing the optional layout (`undefined` is always tag 0, so the numberings coincide); initialization and reassignment tag by member, `is?`/`isnt?` compare tags (folding statically when the answer is known), flow-sensitive narrowing now splits any union — including else-branches — and fully narrowed reads load the payload. Unions now also cross call boundaries: parameters copy the incoming cell in the prologue, member-typed arguments materialize into fresh cells at the call site, results write into a caller-owned result cell, and results compose directly into further union calls. Partially narrowed subset unions work as views — tags stay physical in the storage union's numbering, so subset reads pass the cell through and tests consult the storage members. Fixed-layout aggregate members (objects whose fields are returnable, exact arrays) work too: each aggregate member owns a prepared storage tree allocated with the cell and referenced from slots after the payload word, tagging copies the value into its tree, same-union copies deep-copy the active tree by tag dispatch, and a narrower union retags into a wider one at boundaries (`Pair|string` into `Pair|int64|string`). Object and array literals now check against a union that has exactly one matching member. **Exhaustiveness over `is?` chains landed:** a chain of positive `is?` tests on one union binding whose all-false fall-through leaves no member is exhaustive — the checker turns the last arm into the default (its test can only succeed on that path), so `if v is? int64 { return v } else if v is? string { return 0 }` needs no `else` for return coverage, and a value-producing chain needs none either; a value-producing chain that misses a member reports exactly which (`` `undefined` is not handled by any `is?` arm ``), while statement chains stay free to be partial. A real `match` expression remains a future design (syntax TBD); `is?` chains are the pattern matching until then. **Module-level union bindings landed:** a top-level union is an inert `int64` word (like optionals and objects) whose static tag-and-payload cell — and the aggregate members' storage trees — are allocated with `__static_alloca__` at the binding's first startup assignment, so functions read, narrow, and retag globals exactly like locals. **B1b landed (2026-08-27): recursive members and handle members.** A type alias may refer to itself as a union member of a field (`let Node:type = [value:int64 next:Node|undefined]`, `Tree` with `left`/`right`): the recursive occurrence is `ty.NamedType`, a by-name reference that unfolds to the alias's object type on demand (equal by alias; `is_subtype`/`meet` unfold it; `_canonical_union` spells the alias by reference in every union so all spellings share one member order and tag numbering; expression types are always unfolded). It is allowed only as a union member — a field typed exactly `Node` is an infinite value and an alias whose every member is itself has no base case, both rejected. In the lowering a union cell has three member kinds: word, *tree* (fixed-layout aggregates in prepared cells — locals, parameters, results, as before) and *handle* — a pointer to storage allocated when the member is tagged, always used for recursive references and for every aggregate member of a cell stored inline in an object field (16 bytes, no trees; `[value:int64 next:Node|undefined]` is 32 bytes). Handles are arena-allocated today, through one call site (`_union_handle_value`/`_union_handle_clone`), so the placement stays pluggable; copies are deep — same-union copies, retags and object copies clone the handle's storage, and a recursive alias gets a synthesized `__dewy_copy_<Name>(src):>int64` function so the copy recurses at runtime. Union-typed object fields are supported generally (word/handle members; optionals of a recursive type route through the same machinery since the tags coincide), and the checker narrows *member routes*: `node.next is? Node` refines the route (`sb.array_route_id`) so `node.next.value` reads and writes through the handle until the field or its root is assigned; stores check against the declared field type. Parameters and results typed `Node|int64|undefined` (several members plus `undefined`) now lower as ordinary unions — the "heterogeneous optional parameter type" limit is gone. Not yet: `match`; recursive generic aliases; arrays of a recursive type as a *direct* member position (`array<Node>` inside `Node` needs the array element to be the unfolded object, which the array lowering does not do yet); runtime-length arrays and dictionaries as union members of locals (they are handles only inside fields); moves — `cur = cur.next` deep-copies the tail on every step until liveness-based moves land. Narrowing now also flows past conditionals: the code after an `if` keeps the join of the refinements at the end of every non-diverging path (arm bodies that do not return/break/continue, the `else`, or the all-conditions-false fall-through), so the early-return idiom narrows the union below it even when a non-diverging `else` is present.
- [ ] **B2. Growable arrays.** Push, pop, truncate, runtime-length returns, and escapes into longer-lived storage. Depends directly on phase 1; forces the first real memory-management decision, where the descriptor's `capacity` and `owner` fields either earn their keep or get redesigned. Done so far: the first arena tier exists — `_arena_alloc` in `library/system-linux.dewy` bump-allocates from anonymous `mmap` chunks (process lifetime; scoped arenas still ahead), the prelude merge keeps backend-called runtime helpers alive, and **runtime-length array results** (`:>array<T>` with no exact length) now lower as arena-backed descriptors: the callee copies the returned array into the arena (word-scalar elements for now) and forwarded runtime-length call results pass straight through. Indexing a genuinely runtime-length array still needs the `0 <= i < a.length` refinement proofs (A5); iteration and `.length` work. **Growth syntax decided (2026-08): method-style on the value, never global functions** — `xs.push(x)`, `xs.pop(idx=end)`, `xs.insert(x idx)`, `xs.clear`, `xs.reserve(n)`, `xs.sort`, with indexing as the `__index__` dunder. Conceptually `array` is an ordinary Dewy object type with these methods and an `Index = uint< i => i <? length >` refinement, so the compiler-provided methods should behave exactly as if `array` were defined in Dewy; dunders like `__index__` are the sugar bridge to the global operator form. Container mutation is accessed exclusively through the container; free functions are reserved for genuinely global operations such as `sin`/`cos`/`sqrt`. **Growth methods landed:** `xs.push(x)`, `xs.pop`, `xs.clear`, `xs.reserve(n)` on `let` bindings declared `array<T>` (word-scalar elements for now); growth doubles capacity (minimum 8) and relocates the data into the arena, so raw stack, static, or borrowed data is never written through, and copies stay independent. A `let xs:array<T> = [...]` binding now has the declared runtime-length type with the initializer's exact length kept as a _refinement_ — index proofs keep working until a length-changing method invalidates it, and loop bodies drop refinements of every binding they assign or grow before being checked (this also closed a pre-existing hole where a union narrowing established before a loop survived an assignment inside it). `const` array bindings keep their exact types. **Length facts now track growth:** an exact-length refinement steps through `push`/`pop` and resets on `clear`, and comparisons such as `xs.length >? 0` (or `2 <=? xs.length`) establish proven minimum lengths that step the same way; both are joined across conditional paths, invalidated by assignment and loop-body mutation, and reset per function. `pop` is a proven operation: it is accepted only when the exact length or a guard-proven minimum shows the array is non-empty, and `pop` on a statically empty array is an error. **Runtime-length arrays are now indexable from facts:** the bounds analysis keeps a length interval per runtime-length array (refined by `xs.length >? k`, stepped by growth methods) and `i <? xs.length` guard facts per index binding, so `loop i <? xs.length { xs[i] }` and `if xs.length >? 2 { xs[2] }` are proven; facts are dropped when the index is reassigned or the array shrinks, and joins keep only facts common to all paths. This is the first concrete slice of A5's `Index` refinements. **Positional editing landed:** `xs.insert(value idx)` (grows, shifts the tail up, `idx` may equal the length), `xs.pop(idx)` (takes the element, shifts the tail down; `xs.pop` alone still removes the last), and `xs.truncate(count)` (caps the length, no-op when longer) lower as descriptor operations with element-shifting loops; constant indexes are proven in the checker against the exact-length refinement, runtime ones by the bounds analysis from intervals, minimum lengths, and `i <? xs.length` facts, and `truncate`/`pop` invalidate index facts. The bounds analysis now seeds a growable array's length from an exact initializer, matching the checker's refinement. **Growable array fields (2026-08-26):** array methods and index proofs now work through member routes — `bag.items.push(x)`, `bag.items[i]`, `bag.items.pop` — because length and index facts are keyed by a hidden _route id_ (`BindingRegistry.route_id`, shared by the checker and the bounds analysis) rather than only by binding; assigning the root binding or the field drops the route's facts. Such objects also cross call boundaries now: a runtime-length array field of an object _result_ is a handle slot the callee fills with an arena-backed copy (literal fields, copied values, and forwarded runtime-length call results), value parameters copy the fields into the frame or borrow when read-only, and place parameters grow the caller's object in place. This is the representation step toward a runtime dictionary object. **Growable arrays of objects (2026-08-27, the reporting detour):** `array<Object>` bindings, fields, and results grow like any other array — `xs.push([...])`, `xs.insert(v i)`, `xs.pop`, indexing — with each element a handle to an arena-backed copy (value semantics: the stored object is independent of the value pushed, and a popped element stays valid), and `loop s in objects` iterates them with the loop variable as a *read-only borrow* of the element (no copy per iteration; assigning `s`, its fields, growing its arrays, or passing `@s` is rejected with "borrows the array element" — `let mine:Span = s` copies). Element copies inside copy loops always go to the arena (frame storage would not survive the iteration). Not yet: exact-length array fields inside such elements (they need arena-backed exact arrays), `sort` over objects. `xs.sort` sorts fixed-width integer elements ascending in place through a length dispatcher: up to 32 elements use an insertion sort, longer arrays an LSD radix sort (8-bit digits, one pass per element byte, sign bit flipped for signed widths, arena-allocated swap buffer) — the seed of the planned default sort, which is to choose by length and by whether the elements admit a radix key (comparison sorts such as introsort join the dispatcher when comparators and non-integer elements arrive; later ideas: deriving radix keys from user comparison lambdas where possible, or letting users supply an integral-key lambda). String elements and comparators are still ahead. Still ahead: scoped arenas. (Fixed along the way: lowering side tables keyed by `id(node)` could inherit stale analyses when CPython reused a freed node's id — an allocator-state-dependent miscompile that showed up as intermittent full-suite failures; every re-keyed node is now kept alive for the lowering's lifetime.) Reference design: the circular-deque `vector.c` from the old C implementation (`head` offset + doubling capacity, O(1) push/pop at both ends) — see the representation notes below.
- [ ] **B3. Mutable, growable dictionaries and sets.** Symbol tables, scopes, and string interning. Reference design: the compact-dict `dictionary.c` from the old C implementation — see the representation notes below. Done so far: dictionaries are runtime values on top of growable hidden parallel arrays — `let d:dict<K V> = []` or a literal, `d[k] = v` appends or replaces in place (insertion order is entry order, so iteration order is preserved by construction), `d[k]` is a `V|undefined` lookup, `k in? d` tests membership, `d.length` counts entries, and `loop [k v] in d` iterates grown dictionaries in lockstep at runtime (pure-`and` multiiterators now accept runtime-length arrays). **Dictionaries are runtime objects now (2026-08-26):** `dict<K V>` is the branded object `[keys:array<K> values:array<V>]` (`ty.dict_type`, brand `'dict'`, printed as `dict<K V>`), so every object capability applies — dictionaries are parameters (borrowed when read-only, copied when the callee stores), results, place parameters (`bump(@table k)`), fields, module-level bindings, and literals in any expression position (`lookup(['x' -> 7] 'x')`; an empty literal needs a dictionary type). Lookups, stores, membership, `.length`, and `loop [k v] in d` operate on the `keys`/`values` member routes, whose exact-length facts come from the literal and are dropped by stores. **Lookups are proven (decision 2026-08-26):** `d[k]` is allowed only when the key is proven present and then has type `V` outright — from the literal (`['ann' -> 30]` then `d['ann']`, read at its entry index), a store (`d[k] = v` then `d[k]`, reading the entry the store found or appended), a guard (`if k in? d { d[k] }`, reading at the position the guard's search found, so nothing is searched twice), or iteration (`loop [k v] in d { d[k] }`). Facts are keyed by (dictionary route, key binding or constant), joined across paths (a position survives only when every path found it at the same local), and dropped when the dictionary or the key binding is reassigned; an unproven `d[k]` is a compile error (`dictionary key is not proven present`, neither proven nor refuted) pointing at `.get`. `d.get(k)` is the explicit lookup that may miss (`V | undefined`) and `d.get(k default)` supplies a value (`V`). _Filed for later (2026-08-26):_ negative facts and refinement-typed overloads — a failed `k in? d` guard proves the key _absent_ on the false path, so `.get` there should fold to its default; the intended shape is `get` as overloads over key refinements inside the dictionary's own definition (`get = (key:ProvenKey default:any=undefined) => items[key]` & `get &= (key:~ProvenKey default:any=undefined) => default`), which needs refinements as overload selectors and the negation `~ProvenKey` in the liquid fragment — part of the full refinement system, not the MVP. Search is linear for now; the compact hash-index table can replace it without changing any semantics. **Deletion (2026-08-26):** `d.pop(key)` removes a _proven_ key (the fact requirement of `d[key]`) and yields its value — with the name-only `default` argument (`d.pop(key default=0)`) the key need not be proven and the default results when it is absent — shifting later entries of both arrays down so insertion order is kept — with linear search that is the natural representation; CPython-style tombstones arrive with the hash index, when entry positions must stay stable — and `d.clear` empties the dictionary. After a removal the other keys stay proven but their remembered positions are forgotten; `clear` forgets every key; both step the exact/minimum length facts. **The hash table is real (2026-08-26):** the dictionary object is `[keys values hashes indices live]` — dense insertion-ordered entries with their stored hashes (never recomputed on resize; `-1` marks a tombstone), a power-of-two `indices` probe table (`-1` empty, `-2` dummy, else an entry index) probed CPython-style (`i = (5i + perturb + 1) mod size`, `perturb >>= 5`), and the live count that `d.length` reads. Word keys hash by a multiplicative mix, strings by FNV-1a over their bytes. The table is built lazily on first use, kept under 2/3 load counting tombstones, and rebuilt (compacting the entries) when a store would exceed that; `pop` is O(1) — tombstone the entry and dummy the slot, so remembered positions stay valid — and iteration compacts first when removals left dead entries. Slots are `int64` for now (narrowing them to 1/2/4 bytes by entry count is the remaining CPython detail). **Sets (2026-08-26):** `set<T>` is the branded object `[keys hashes indices live]` — the dictionary without values, on the same table machinery — with `set[a b c]` literals (constant members, duplicates collapse at compile time; an empty literal needs a set type), `s.add(x)`, `x in? s`, `s.pop(x)` (a _proven_ member, per the Python-exception rule; yields the member — `pop` means the same thing on arrays, dictionaries, and sets: remove the identified entry and give it back, per the name-uniformity direction that already collapsed length/size/shape into `length`), `s.pop(x default=v)` for a removal that may miss (no proof; the member or `v`, so `default=undefined` yields `T|undefined` — the uniform `default=` rule replaces Python's `discard`), set algebra `|`/`or` (union), `&`/`and` (intersection), `-` (difference), `xor` (symmetric difference) producing new sets, `d1 | d2` merging dictionaries Python-style (the right value wins for shared keys, left insertion order kept), and the views `d.keys` (a fresh `set<K>`, so `d1.keys and d2.keys` is set algebra), `d.values` (a fresh `array<V>` in insertion order), and `s.values` (a fresh `array<T>`), `s.clear`, `s.length`, and `loop x in s` over the live members in insertion order. Mutating a dictionary or set inside its own loop (`pop`, `add`, stores, `clear`) is a compile error — Python raises "changed size during iteration" at runtime, so by the rule above it must be rejected statically. Sets are not indexable. Open naming question: `s.add(x)` versus `xs.push(x)` — the same uniformity argument may collapse `add` into `push`. Still ahead for both containers: bidirectional dictionaries, compound set operators (`|=` etc.), narrowing index slots, equality/ordering rules, and non-word keys.

**Design rule when patterning after Python (2026-08-26):** anything that would raise an exception in Python must be proven safe at compile time in Dewy or it does not compile (`d[k]`, `d.pop(k)`, `xs.pop`, indexes, `remove` on sets); the non-exception behavior stays the same as Python (names, insertion-ordered iteration) unless a clearly more Dewy-esque shape exists, and an explicit alternative (`get`, `default=`, `discard`) covers the may-miss cases.

**Combining sequences (2026-08-26):** `+` is not concatenation. It stays arithmetic so it can remain addition for numbers and (later) arrays. Strings combine by interpolation (`"{s1}{s2}"`, `"Hello {name}"`); arrays combine by spread in a literal (`[arr1... arr2...]`, `[0 xs... 1]`). Loop-built strings still need `join` (e.g. `myarr = ['a' 'b' 'c']` then `myarr.join` or `myarr.join'|'` i.e. `join` takes an optional separator char) (B8). Array-literal spread is construction syntax, tracked with the other `...` work rather than as a `+` overload.

**Runtime representation notes for dictionaries, sets, and deque arrays.** The intended full representations are based on the old C implementations on the `C_Clustered_Nonterminal_Parser` branch (`src/dictionary.c`, `src/vector.c`):

- Dictionaries (and sets) use the compact two-structure layout: a sparse `indices` probe table mapping hash slots to entry positions, plus a dense `entries` array of `(hash, key, value)` in insertion order; iteration walks the dense entries array. The two structures resize independently (indices rehash at ~2/3 load; entries double). **Probing decision (2026-08):** do _not_ copy the C implementation's PRNG/LFSR step for collision resolution; use CPython's scheme instead — open addressing with `i = (5*i + perturb + 1) mod size` and `perturb >>= 5`, where `perturb` starts as the full hash. The first probes stay near the initial slot (cache-friendly), the high hash bits still break up clustering, and once `perturb` reaches zero the recurrence is a full-period permutation of a power-of-two table, so every slot is visited. Also worth taking from CPython: a power-of-two index table sized so load stays under 2/3, index entries narrowed to 1/2/4/8 bytes by entry count, and hashes stored in the entries so rehashing never recomputes them. **Current state:** only the dense-entries half exists (parallel key/value arrays with linear search); adding the index table changes no semantics. For the remaining open questions (deletion via index-table tombstones, resize policy, hash mixing) the default is to pattern after CPython's dictionary wherever its choices fit Dewy.
- **Semantic guarantee to preserve from day one: dictionaries and sets iterate in insertion order.** The current compile-time dictionaries (hidden parallel arrays in literal order) already satisfy this; nothing may regress it when the runtime representation lands. Deletion semantics in the C code were unfinished (a `DELETED` sentinel existed but was unused), so deletion behavior is an open design point, not something to copy.
- Vectors are circular deques: `head` offset + `size` + `capacity` with modular indexing, capacity doubling (power-of-2), giving O(1) push/pop at both ends. This is a candidate representation for growable arrays where front-insertion matters; the known middle-insertion off-by-one in the C code is a bug, not a spec.

### Library housekeeping

The library is now split into a portable layer and per-target layers: `library/linux/io.dewy` (`_write_stdout`/`_write_stderr` over the `write` syscall) and `library/linux/system.dewy` (arena, `sleep`, file access) are the Linux target layer; `library/io.dewy` (`print`/`printl`, integer and boolean printing, interpolation streaming), `path.dewy`, and `units.dewy` are portable and build only on the target primitives. Target gating is native and mirrors udewy exactly (udewy is meant to be valid Dewy): `$target` is the backend name (`x86_64`, `riscv`, `arm`, `c`, `wasm32`) as a compile-time string, `$target =? "..."` folds during checking (Dewy adds the conveniences `$target in? ["x86_64" "riscv" ...]`, `not =?`/`not in?`, prefix `not`, and `and`/`or` over such conditions), and an `if` on such a condition skips its dead arms entirely (unchecked, so they may import files that only exist for other targets) while splicing the live `{}` body into the enclosing scope; plain literal conditions (`if true`) keep ordinary flow semantics with every arm checked. `library/io.dewy` imports its own primitives with `if $target in? ["x86_64" "riscv" "arm" "c"] { from p"linux/io.dewy" import (_write_stdout _write_stderr) }` (udewy's `host.udewy` spells the same thing as one `if $target =? ...` per target). `$supported_targets = ["x86_64" ...]` (backend names, as in udewy) rejects compilation for other targets. Open design point for later: the target list in `dewy/targets.py` is slated for an overhaul into fuller triples (`x86_64-linux-musl`, `c-posix`, `wasm32-wasi`, ...); per-target gating then gets cumbersome (`$target in? [...]`), so the likely shape is a structured target (`$target.os =? "linux"`, `$target.arch`, ...) — to be settled in a dedicated discussion, not now. `dewy/semantic/prelude.py` now lists only the portable files plus the OS _services_ layer (`linux/system.dewy`, which needs portable types such as `Duration`), selected from the target passed down from the CLI (`dewy -t`). The stale `core-*.dewy` files are parked in `library/old/`. A new target provides its own `io.dewy`/`system.dewy` with the same bindings.

- **Core data structures as Dewy libraries (very long term).** Arrays, dictionaries, sets, strings, rationals, and fixed-point should eventually be implemented _in Dewy_, in library code, rather than in the compiler: the compiler would keep only the primitives they need (raw storage and layout capabilities, the `__index__`-style dunder bridge, the fact/proof hooks) and the analyses. Rationals and fixed-point already work this way (prelude object types with Dewy-written operations and only routing in the checker); arrays and dictionaries do not yet — their methods, index proofs, key facts, hash table, and iteration are compiler-emitted. The payoffs: users can write their own efficient data structures that participate in the same proofs (length facts, proven keys, refinements) instead of only the built-in ones; the language's own containers become ordinary code that can be read, replaced, and specialized; and the core compiler shrinks. The prerequisites are the items already on the roadmap — user-written generics (B7), refinements as contracts on user code (the full A5 system), the storage/placement primitives from the ownership model, and a way for library types to declare facts the analyses can track — so this is the direction those slices should keep in view rather than a slice of its own.

### Ownership and storage model (design decision, 2026-08; reframed 2026-08-25)

**The user-level goal fixes the model.** Dewy should feel like a memory-managed language — no lifetimes to annotate, no `free`, nothing leaks, no aliasing surprises — while being efficient by default and letting experts inspect and adjust placement when they want to. The rule that makes this possible is already fixed by `semantic/value_semantics.md`: every binding uniquely owns its value, assignment has value behavior, copy-on-write is never the universal mechanism. Given that, the model is:

1. **Unique ownership with deterministic release is the baseline.** Every runtime-sized value has exactly one owner; when the owner leaves scope or is overwritten the storage is released, without the program saying so. Assignment is a copy _semantically_ and the compiler turns it into a move whenever the source is provably dead afterward (liveness over the effect summaries), a borrow when the consumer is provably read-only (already implemented for parameters), and an explicit copy otherwise. This is Rust's ownership model without its surface syntax — value semantics means nothing aliases, so nothing needs annotating — with no GC and no refcount traffic. The key property: **the analyses only ever change speed, never whether a program is valid.** A program that the move analysis cannot optimize still compiles and still releases everything. Needs a real allocator: udewy has none (`__malloc__`/`__free__` are placeholders), so a size-class free-list allocator over `mmap`, written in Dewy in the library, is the first piece of this tier.
2. **Placement optimizations, applied by the compiler when proofs allow.** Static sizing (compile-time sizes stay in frame `__alloca__`/static storage/caller-owned result trees — already the default for everything fixed, and later also for structures that are dynamic in shape but static in inputs per the effect analysis), stack allocation, and _scoped arenas_ when escape analysis proves scope-shaped lifetimes (most locals; whole phases of a compiler). Because these are optimizations with the baseline as fallback they may be conservative. The scoped-arena design below is the mechanism for this tier.
3. **Explicit control for experts.** Following Jai/Odin: an implicit _context allocator_ threaded through every call, so a caller can push an allocator (arena, pool, tracing allocator) and libraries allocate from it without having been written to accommodate that; values record their allocator (the descriptor's `owner` word) so release always goes to the right place. The difference from Jai is that Dewy keeps checking: a value leaving a pushed-allocator scope is proven not to escape, copied out, or rejected at compile time — never silently dangling. Named regions, user placement (syntax TBD, see the units/`type of unit` notes), and a userland `Rc<T>` for genuinely shared or cyclic data (below) complete this tier.

**Where copies remain.** Most transfers are last-use and become moves (returning locals, passing values straight through, build-then-store, reassignment of dead values). Copies that stay are either semantically required (the source is used again — two independent values under value semantics) or analysis-limited (control-flow-dependent liveness, moves inside loops with reads after, closure captures, containers of containers, routes through `@` places). Eager copies have predictable cost (no COW cliff), and a _copy report_ diagnostic — every copy of runtime-sized storage in a function, with sizes when known — is planned with the move analysis so that hand-optimizing memory is a guided activity.

**Current state versus this model.** Today's single process-lifetime arena (`_arena_alloc`, never released) is a placeholder for tier 1, not the destination; the array descriptor's `capacity`/`owner` fields are the ownership metadata for the model. Pending work in order: (a) the library allocator and drop-at-scope-exit for runtime-sized locals (arrays, dictionaries, unions with runtime-sized members), (b) the liveness pass and move rule, (c) the scoped-arena optimization below, (d) the context allocator and explicit placement.

**Scoped arenas (design, 2026-08).** Today there is exactly one arena: a process-lifetime bump allocator (`_arena_alloc` in `library/linux/system.dewy`) that every runtime-sized allocation uses — growable-array relocation, dictionary arrays, runtime-length results, `argv` strings, sort buffers — and nothing is ever released. Under the model above, scoped arenas are the tier-2 optimization that makes allocations die with a scope when that is provably safe.

- _Regions are runtime values, not marks on one stack._ An arena is a small object `Arena = [cursor end chunks ...]` created lazily on first allocation; allocating from a region bumps that region's cursor, growing it by `mmap`ed chunks; releasing a region returns its chunks to a free list for reuse (no `munmap` in the hot path). Separate regions (rather than save/restore marks on one bump stack) are chosen because a growable structure owned by an outer scope must be able to grow _while inner scopes are live_ — `xs.push` inside a loop or callee must allocate in `xs`'s region, which a single stack cannot do without copy-outs — and because a region-as-value is exactly the seam for the context allocator: a descriptor's owner may be a user-provided arena or allocator handle rather than the compiler's default.
- _Ownership in the descriptor._ The array descriptor's `owner` word becomes the owning region/allocator; growth and relocation allocate from `owner`, never from "the current scope". Dictionaries' hidden arrays and runtime-sized union members follow the same rule.
- _Default regions._ The module region owns module-level structures (process lifetime, as now). A function whose body allocates gets a _frame region_ only when escape analysis proves its structures do not leave the frame; otherwise those structures are owned individually (tier 1). Loop-iteration regions (allocations proven not to escape the iteration) are the second step; explicit user regions the third.
- _Escapes._ Runtime-length results are allocated directly in the _caller's_ region or allocator — the caller passes it as a hidden argument, the same way destination-ABI results already pass a result pointer — so nothing is copied twice and the callee's own region can be released. Stores into outer structures are value copies made in the destination's allocator. Whole-value rebinding of runtime-length arrays across scopes waits for the liveness pass.
- _Slices._ (1) Runtime regions + module and frame regions + owner-based growth + caller-region results; (2) loop-iteration regions with escape proofs; (3) explicit regions and the context allocator. Measurement target: a loop that rebuilds a 1000-element array 10 000 times runs in constant memory.

An additional, opt-in systems escape hatch is now outlined in [`semantic/user_managed_storage.md`](semantic/user_managed_storage.md). A library-defined `Rc<T>` should be an ordinary explicit handle value, not an escaping `@` place and not Dewy's default storage strategy. Making that implementable in user code eventually requires deterministic copy/transfer/release hooks, typed unsafe allocation and layout capabilities, lifetime-bounded places into managed payloads, and atomics only for a later cross-thread `Arc<T>`. This is design work after the current arena and ownership slice, not a reason to introduce universal reference counting.

Unannotated integers behave as arbitrary precision. Explicit fixed-width annotations rollover as that width. Range analysis is the pass that proves whether a particular `int`, iterator, or arithmetic intermediate can be represented with a concrete `intN` under the hood without changing those semantics.

Exact division of big integers waits for rationals over big integers. Sequential 7:04 → parallel ~2:30 before the cache. Next tier if needed: cache the typechecked prelude too (needs a snapshot per compile or non-mutating lowering, since lowering retypes prelude HIR in place).

**Literal types (2026-08-27):** a literal in a type context is its singleton type — integer and string literals and packed based literals (`x:5`, `s:"one"`, `b:0x"6869"`); the type contexts are annotations, the right side of `name:type =`, and an explicit `<…>` type block (the disambiguating spelling David proposed: `<1 | 2 | "one">` is a type, while the bare form in value position would be `or` over values). Unions of literals are enumerations (`Mode:type = <1 | 2 | "fast">`, narrowed by `is?`, lowered as ordinary tagged unions — literal members are word members), and a literal-typed parameter specializes an overload with its own result type (`((n:int64 d:0):>DivZero => DivZero) & ((n:int64 d:int64):>int64 => n // d)` — a literal-zero call is typed `DivZero`, any other call `int64`). _Gap surfaced by that example and closed the same day:_ the general method admitted a runtime zero and `n // d` with an unproven runtime divisor compiled silently; refined parameters and the nonzero-divisor obligation (below) fix both, and the example now reads `(n:int64 d:int64<i => i not=? 0>)`. ## Array, object, and other compile-time versus runtime representations

Language-level assignment, passing, and return are copies; `@` is the spelled place. See [`semantic/value_semantics.md`](semantic/value_semantics.md). Sharing a pointer for `let b = a` is an elided copy, not the user-visible rule.

The source-level type of a value describes its semantics, not a mandatory machine layout. Lowering should retain only information that can affect the program at runtime. Facts already established by typing, refinement, control-flow, or effect analysis should normally become constants in the emitted program rather than fields stored beside every value.

The current backend still uses a canonical pointer to a 48-byte descriptor containing `data`, `length`, `capacity`, `stride`, `flags`, and `owner` for most arrays. Two proven cases omit it:

- Module-scope `const` arrays whose binding-identity use set contains only `.length`, indexed reads, and proven-safe direct-call boundaries can use raw static storage. Compatible one-word literals and function references use udewy's internal `__static_words__`, while exact based bytes use their static data pointer.
- A function-local `let` or `const` binding initialized directly by an exact-length `ArrayLiteral` uses a fresh `__alloca__` element buffer when all uses are `.length`, indexed reads or writes, ordinary same-function copies, or analyzed call boundaries. Each downstream binding gets independent element storage when either value could be mutated. Length is folded from the exact type, element stride is compiled into address arithmetic, and width-correct loads and stores address the buffer directly. Semantic checking still rejects indexed writes through a `const` binding.

For a statically resolved direct or selected-overload call, a parameter that only observes length, indexed reads, or other read-only calls is adapter-safe. Lowering wraps raw local/static data in a temporary canonical descriptor in the call prelude without copying elements; the callee ABI and indexing remain descriptor-based. When the callee may write or the call cannot be analyzed, arrays are copied into fresh descriptor-backed element storage first. Exact copies are unrolled; runtime-length copies use a counted loop over the descriptor length. Read-only exact static bytes use borrowed-static flags.

Recursively fixed array and structural-object returns use a hidden destination supplied by the caller. The caller allocates the complete mutable storage tree in its own frame, including exact nested array descriptors and buffers or exact array-valued object fields. The callee initializes or recursively copies into that storage before returning, and a directly returned call forwards the same destination through wrapper functions. No callee-local mutable result storage escapes. Local binding, assignment, element storage, object-field storage, and argument passing use the same recursive value-copy rule. Runtime-length arrays can be copied while the destination remains in the current frame. Results with runtime-dependent storage, unresolved backing-storage lifetimes, and other escapes remain pending. Control-flow representation joins, general or transitive effect analysis, indirect/method read-only adapters, and descriptor-free specialized direct-call ABIs also remain pending. At present arrays cannot change length; `capacity`, `stride`, and `owner` are not read by generated programs.

A named scalar or array passed as `@name` uses non-escaping addressable storage for the duration of the call. Scalar cells use width-correct loads and stores. An array place exposes the caller's descriptor, so direct element writes reach the selected storage; replacing a recursively fixed array writes into the complete storage tree already owned by the caller rather than publishing callee-local pointers. The caller reloads its binding after the call, including when one place parameter forwards the place to another. Structural objects already have stable recursively fixed storage, so an object place passes that address directly without another cell; field writes and whole-object copying both update the caller's storage. Field and index selectors project the root place to the final storage address, evaluating computed indices once. Disjoint constant indices or object fields may be passed together; dynamic indices and prefix routes are conservatively treated as potentially overlapping. This ABI deliberately requires exact source/parameter type equality and does not allow a place to be stored or returned. Whole-value rebinding of a runtime-length array place remains pending because the destination storage size may change.

The intended rule is that each value receives the least runtime representation needed by all of its reachable uses. For arrays this includes:

- An immutable literal used directly by another operation can lower to static element data, or directly to an udewy literal operand, with no descriptor.
- A fixed-length mutable local array needs writable element storage, but does not inherently need metadata beside that storage.
- A view whose length is known only at runtime may need `(data, length)`.
- A borrowed byte view that may be mutated needs enough dynamic state to distinguish borrowed from owned storage and perform copy-on-write. If analysis proves that it is never mutated, that state is unnecessary.
- A future growable array may need `(data, length, capacity)`. Capacity should not exist merely in anticipation of operations that the value never performs.
- Element stride follows from `array<T>` and should be compiled into address arithmetic. A runtime stride is justified only by genuine type erasure, such as an existential container or an FFI contract whose element layout is not statically available. Merely placing differently typed arrays in different fields of one object does not erase their element types.
- Ownership or lifetime metadata is needed only when the selected memory management strategy must inspect it dynamically. It need not be a field on every array merely because some arrays borrow storage.

This produces a spectrum rather than a second universal layout: no runtime value, raw data only, a scalar tuple such as `(data, length)`, or a full descriptor. Known `.length` operations and element widths are substituted directly at their uses. A descriptor is materialized only at a boundary that actually requires the canonical handle representation.

The same principle applies beyond arrays:

- Object fields can remain independent scalar values, and unused fields can be absent, while an object that escapes or crosses a canonical ABI boundary may require materialization into memory. Scalar replacement must preserve the language's object value and mutation semantics.
- Exact string literals should remain semantic singletons until context selects UTF-8 bytes, Unicode scalars, graphemes, or a runtime string. UTF-8 data, grapheme boundaries, byte length, and grapheme length should be materialized only when the selected operations require them.
- Optional and union tags can disappear after exhaustive narrowing, or be encoded in an unused payload value when a valid niche is proven. A general tag-and-payload representation remains the fallback.
- Ranges and iterators whose bounds and state transitions are known can lower directly to loop scalars instead of heap- or stack-resident iterator records.
- Function values need only a code pointer when no environment is captured; closures require an environment only when captures survive lowering.

Representation selection must happen after semantic typing. Two values with the same Dewy type may therefore use different machine representations without that difference becoming observable in Dewy. The compiler must insert an adapter or materialize the canonical form when differently represented values meet at control-flow joins, indirect calls, separately compiled interfaces, FFI boundaries, or unspecialized function parameters. Direct calls may instead be specialized so that compile-time facts continue across the boundary.

Choosing a smaller representation requires proofs about every relevant use:

- use analysis determines which metadata and operations are observed;
- escape and lifetime analysis determines whether storage or descriptors must survive the current scope;
- mutation, effect, and alias analysis determines whether facts remain true across assignments and calls, and whether borrowed storage needs copy-on-write;
- control-flow analysis selects a representation valid for every path and identifies where values with different representations merge;
- ABI analysis determines where a stable canonical layout is externally observable or needed for indirect access.

When a proof is unavailable, lowering should use the canonical representation rather than changing semantics or inserting speculative behavior. This makes the full descriptor a correctness fallback, not the default cost paid by every value.

### Liquid Refinement System

Dewy does not have a fully arbitrary refinement type system. Refinements are restricted to a well-behaved liquid proposition language that the compiler can normally infer and prove automatically. General Dewy expressions do not become valid refinement predicates merely because they produce a Boolean.

The intended proof boundaries are:

- an automatically proven refinement has no runtime cost
- an explicit runtime check refines the value on every path where the check succeeded, including after an early exit that discarded the failing case (`if not condition then return`, and similar)
- a checked proof or lemma may discharge an obligation the automatic liquid solver could not establish on its own
- an explicit `unsafe` claim may assume an obligation without a runtime check or checked proof; it is a real safety boundary and remains an audit obligation

A claim accompanied by a compiler-checked proof is no longer unsafe. Commentary, an unchecked certificate, or an omitted proof does not discharge the unsafe obligation. The proof language may eventually be richer than the automatic solver, but facts imported back into ordinary refinement checking must have a conclusion the liquid proposition language can represent.

The initial liquid proposition language should focus on the facts most useful to ordinary Dewy programs: Boolean combinations, equality and ordering, linear integer arithmetic, literal and type/tag tests, lengths and other trusted pure measures, and simple relationships between parameters and results. Arbitrary function calls, unrestricted quantification, effectful expressions, and general nonlinear arithmetic are outside the automatic refinement language. The exact fragment and qualifier-inference strategy remain to be specified.

> NOTE: this doesn't preclude calling functions in refinements. Suitably pure functions can be used. E.g. if the contents of a function call and any subsequent internal calls were inlined and that inlining would be a valid refinement, then that function ought to be valid.

Refinement propositions should have their own semantic representation rather than reusing unrestricted HIR expressions. Reasoning about semantic arbitrary- precision `int` must also remain distinct from reasoning about fixed-width rollover arithmetic: the latter requires bit-vector-aware rules or a separate (automated or user-provided) proof that overflow cannot occur.

Within those constraints, the refinement system shall work as follows:

- any type may receive a parameterize block (e.g. `T<p1 p2 etc...>`), including types that don't take any explicit parameters
- supported liquid propositions in the parameterize block are the refinement conditions for that type. The compiler attempts to prove them statically from inferred facts, control flow, and declared contracts

```dewy
NonEmptyArray = array<length>?0>  # retains the generic T from array, e.g. can do NonEmptyArray<int> because we didn't fill in the type

MyStruct:type = [a:int b:bool c:string]< a>?10 b=?true c not=? 'apple' >
```

- additionally assignment expressions in the conditional block can be used to directly indicate some field will always have that value. This is mostly just a convenience for a common case, e.g.

```dewy
SingleValuedArray = array<length=1>  # identical to array<length=?1>
```

- entries in the parameterize block are distinguished syntactically: an expression whose top level is a `?`-comparison (`>?`, `=?`, `not=?`, etc.), or a lambda, or an assignment is a refinement condition; every other expression is a parameter value. The expression selected as a refinement condition must still belong to the supported liquid proposition language. So a literal boolean is unambiguously a parameter, and no wrapping/escaping syntax is needed:

```dewy
trues:array<true length=5> = [true true true true true]  # element type is literal-type true, length refined to 5
```

In the rare case where a precomputed boolean should act as a condition, spell it explicitly: `cond =? true`, or use a lambda. A refinement condition that statically reduces to a constant (always true / always false) is a compile error, since it is either vacuous or unsatisfiable and almost certainly a mistake.

- inside the parameterize block, if the type is a structural type, all members on that struct are in scope to reference for conditions. Members shadow outer bindings; outer scope is otherwise visible (needed for e.g. `length =? n` against an enclosing generic parameter)
- inside the parameterize block of nominal types, there is no `self`, so you have to use a lambda to access the value

```dewy
Positive = int< i=>i>?0 >  # to refer to primitive types, use a single-argument lambda
Positive:type = [i:int]< i>?0 > # similar-ish outcome without needing the lambda
```

Note that `[i:int]< i>?0 >` is _not_ an alternate spelling of the same type: it is a structural wrapper type containing an int, which is a different type from a refined `int` (see structural splicing below for how such a wrapper could be made usable as an int).

- parameterizing a type returns another type, so parameterization may be stacked; each application only narrows (predicate intersection), so the semantics are well defined and stacking is allowed uniformly, whether through intermediate identifiers or directly (`MyStruct<c1><c2>`). Direct stacking is unidiomatic and may warrant a style lint, but not an error

```dewy
T1 = MyStruct<condition1>
T2 = T1<condition2>  # T2 requires both conditions
```

Mainly useful for e.g. letting you return a type and some consumer can further refine it if they need. In general, from an implementation point of view, applying a parameterization is much like doing a partial application on the type object: you're setting particular members, registering refinements, etc.

- refinement checking has three meaningful outcomes: proven, refuted, and unknown. Unknown is not the same as false and should not be reported as such
- when the checker cannot prove a required refinement at a use site, the programmer may: add an explicit runtime check whose success refines the value afterward, provide a compiler-checked proof or lemma, strengthen the surrounding contract, or make an explicit `unsafe` claim that takes on the proof obligation without a runtime check
- unsafe claims should be lexically explicit, scoped as locally as practical, and visible to diagnostics and tooling. If used to eliminate bounds checks, select a narrower representation, or justify other partial operations, violating the claim may produce undefined behavior
- proof-failure diagnostics should report the known facts, the required fact, and the missing relationship, and should distinguish a refuted obligation from one that is merely outside the solver's knowledge or supported fragment

### Structural splicing into the nominal type tree

Structural requirements may be combined with a fresh nominal descendant. `type of Parent` is the operation that mints the nominal identity; `&` only intersects the resulting type with the structural requirements:

```dewy
Posit64:type = (type of float64) & [sign:bit regime:array<bits> exponent:array<bits> fraction:array<bits>]< regime.length + exponent.length + fraction.length =? 63 >
__as__ &= (x:Posit64):>float64 => { some algorithm to convert posits to floats }
```

Rules and semantics:

- `type of Parent` creates one fresh nominal child of `Parent`. Intersecting that child with a structure does not mint a second type or add another edge to the nominal tree
- `A & B` is always non-generative type intersection. A hybrid retains any nominal ancestry already present in its operands, and otherwise follows structural/duck-typed equality
- a structural type with a representation different from a representation-bearing nominal ancestor requires a corresponding `__as__` overload when a use reaches that ancestor's canonical representation. The absence is checked lazily at use sites (definitions may appear after the type, in any order at module level), and it is a type error to actually need the conversion when none is defined. Marker ancestry with no canonical representation, such as `exception` and `error`, introduces no conversion by itself
- `x is? float64` is true for a `Posit64` instance; the spliced type genuinely is a descendant of the nominal type
- the nominal type tree itself is single inheritance, but structural intersections may require membership in multiple nominal families (`MyType = int & float64 & [...]`), with one `__as__` overload per representation-bearing nominal parent
- nominal types are immutable / have no internal fields to mutate, so coercion never creates mutation-aliasing concerns; `__as__` produces a fresh value with ordinary value semantics
- `as`/`__as__` in general must be invoked explicitly; the sole implicit case is a spliced type flowing to a context requiring one of its nominal ancestors
- coercion happens at _canonical-representation boundaries_, not call boundaries. A generic bound like `<T of float64>(left:T right:T)` binds `T = Posit64` directly with no conversion; `__as__` is inserted only where the canonical machine representation is actually required (e.g. inside a builtin body), per the representation-selection rules described earlier in this document. Consequently, overload resolution prefers a representation-preserving match over one requiring `__as__`, so defining posit-native operations opts out of coercion per-operation
- conversion path resolution: an explicitly defined direct `__as__` always takes precedence over a composed path. Composed paths (chaining `__as__` up the ancestry, e.g. `Tracked -> Posit64 -> float64` for `Tracked = Posit64 & [...]`) are allowed when unambiguous. With multiple nominal parents, diamonds are possible (`X = int & float64 & [...]` at a boundary expecting a common ancestor); if multiple composed paths exist at a use site, that is a type error, resolved by defining a direct conversion. The error surfaces only at ambiguous _use_ sites — the mere existence of multiple paths is fine (opt-in lint at most) — and the diagnostic must name the competing paths and the definition sites of the `__as__` overloads involved
- a pure nominal descendant with no structural body is spelled as an ordinary expression: `UserId = type of int`
- extending an existing hybrid structurally does not need or create another nominal type: `DetailedPosit = Posit64 & [source:string]`. It remains nominally a `Posit64` while requiring the added field

Structural object intersections merge requirements by field name. A field present on only one side is retained. For a field on both sides, the required type is the intersection of the two field types. The mutability declarations must agree; mutable and const requirements for the same field are incompatible rather than silently selecting one. If a required field type normalizes to `never`, the entire object intersection is uninhabited and a declaration that presents it as a constructible type is rejected.

### Generativity of type expressions

- `type of T` is the sole generative type expression. Each evaluation mints a distinct nominal child. Type expressions are ordinary expressions and function bodies re-evaluate on every call, so a factory containing `type of` returns a fresh type per call
- `A & B` never mints identity. Purely structural intersections use duck-typed equality; intersections carrying a nominal component retain that existing nominal identity. If a combined structural type needs unique identity, write `(type of any) & [...]`
- binding a generative result once gives it stable identity; aliasing or structurally strengthening that binding does not mint again

```dewy
Tagged = (T:type) => T & [tag:string]
TaggedInt1 = Tagged(int)
TaggedInt2 = Tagged(int)  # equal to TaggedInt1: the body contains no generative expression

FreshTagged = (T:type) => (type of T) & [tag:string]
Fresh1 = FreshTagged(int)
Fresh2 = FreshTagged(int) # distinct nominal types
```

- generics do not change this: genericizing an expression is sugar for making it a function taking a type parameter. Re-evaluating a body containing only intersections produces an equal structural type; re-evaluating a body containing `type of` mints a fresh type. Generic instantiation is not implicitly memoized
- type annotations (on parameters, returns, bindings) are conceptually evaluated once, at typechecking time — checking happens once even if the function is called many times. Default values, by contrast, are re-evaluated on every call (so `(a:array = []) => ...` gets a fresh array per call, avoiding the shared mutable-default trap). A generative type expression in default-value position therefore mints a fresh type per call, consistent with both rules
- builtin parameterization like `array<int>` is non-generative: parameterizing an existing type is partial application on the type object (narrowing), not minting a descendant. The dividing line is simple: only `type of` mints

### Constructing nominal and hybrid values

- a unit-like nominal type has one canonical inhabitant, written with the type's own name. `MyCustomError = type of error` can therefore be returned as `return MyCustomError`; an explicit `MyCustomError()` spelling is not currently part of the design
- it remains open whether the type value and this canonical inhabitant are literally the same semantic object or share only the spelling selected by type/value context
- a hybrid nominal/structural value is constructed by applying the type to its object portion: `MyComplexError[extra='context' fields=42]`. The object literal must provide every required field with a compatible type, and the result carries the hybrid's nominal ancestry
- structurally strengthened aliases use the same construction form and require the combined fields. They are not separate nominal variants: `Base | (Base & Extra)` normalizes to `Base`
- a pure nominal descendant is not automatically unit-like merely because it declares no object fields. A representation-bearing parent may require a payload; for example, `UserId = type of int` describes an integer-like nominal descendant rather than a singleton

### Array type literal syntax (`T[]`)

TypeScript-style postfix `[]` is sugar for the builtin `array` type (which is the canonical representation; it is a structural type with a `length` field):

```dewy
int[]          # array<int>
int[5]         # array<int length=?5>
int[3 4]       # array<int length=?[3 4]>   multidimensional shape
int[][]        # array<array<int>>          left-associative
(bool|string)[]  # array<bool|string>
bool|string[]    # bool | array<string>     postfix [] binds much tighter than |
```

- since Dewy has no separate type-level grammar (types are ordinary expressions), this parses in the value grammar as juxtaposition of a value with an array literal — the same surface form as indexing. Juxtaposition resolves to different operations based on operand types (like `a(b)` resolving to `__mul__` vs `__call__`), so a type juxtaposed with an array literal resolves to array-type construction. Indexing a type object is otherwise meaningless, so nothing legitimate is displaced
- precedence is that of index juxtapose (high, same tier as call/index, possibly tied with type-param juxtapose)

> NOTE: these are implementation notes/tasks under the liquid refinement design above.

- [ ] Define the liquid proposition grammar, trusted pure measures, and finite qualifier vocabulary used for inference. Unsupported general Dewy expressions must not silently enter refinement checking.
- [ ] Flow-sensitive refinement typing. Track value facts through ordinary control flow: x != 0, 0 <= i < a.length, literal values, unions/intersections, exclusions like T & ~0, etc.
- [ ] Refinement-aware function contracts. Let parameter and return types express predicates and relationships between values, including overloads selected by refinements.
- [ ] Static proof before implicit partial operations. Operations like indexing, division, narrowing casts, invalid shifts, etc. compile normally only when the compiler can prove their preconditions.
- [ ] Explicit runtime validation boundary. Runtime checks should appear only when the programmer writes an explicit check or checked operation; successful checks refine the value afterward.
- [ ] Explicit unsafe escape hatch. Permit the programmer to assert an unproven invariant without a runtime check, with unsafe marking the proof obligation clearly.
- [ ] Optional checked-proof boundary. Allow a proof or lemma to discharge an obligation the automatic liquid solver reports as unknown. Checked proofs erase the corresponding unsafe obligation; unchecked evidence does not.
- [ ] Symbolic state tracking across mutation. Model operations such as push, pop, truncate, mutation, and function calls as state transitions, then propagate or invalidate refinements precisely.
- [ ] Effect and alias tracking. Know what functions can mutate, allocate, block, access shared state, change collection length, etc., so existing proofs survive calls whenever justified.
- [ ] Automatic arithmetic/range reasoning within the liquid fragment. Use a solver capable of proving common equalities, inequalities, ranges, and simple relationships without programmer-written proof terms; solver failure or an unsupported proposition produces unknown rather than false.
- [ ] Inference-first ergonomics. Ordinary imperative code should usually verify without annotations; explicit contracts/invariants should be needed mainly at abstraction boundaries and complex loops.
- [ ] Semantic types separated from machine representation. Let types such as arbitrary-precision integers describe semantics, while range analysis chooses i8/i32/i64/... representations when provably equivalent.
- [ ] Information-preserving casts by default. Normal casts must preserve value/precision; potentially lossy or fallible conversions should be explicit and typed accordingly.
- [ ] Typed failure instead of hidden traps. Allocation failure and other genuinely dynamic failures should appear as result/error values or explicit effects rather than invisible exceptional paths.
- [ ] Verifier-friendly standard library. Give core operations precise contracts—for example map preserves length, pop decrements it by one, slice has a known resulting length—so proofs compose automatically.
- [ ] Useful proof diagnostics. When verification fails, report known facts, required fact, and the missing relationship, rather than exposing solver internals.
- [ ] Optimization driven by proofs. Reuse refinement information for bounds-check elimination, integer-width selection, dead-branch elimination, specialization, and other lowering decisions.
- [ ] Idiomatic code designed to be provable. Make the language’s normal APIs and control structures naturally expose the invariants the verifier needs, rather than treating verification as an add-on.

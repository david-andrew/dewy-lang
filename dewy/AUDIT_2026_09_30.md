# Dewy project audit — 2026-09-30

Dewy's intended language is coherent and worth pursuing. The main threat is that
semantic richness is becoming entangled with implementation identity, physical
storage, and compiler work. Better borrowing and a faster allocator will help,
but they will not, by themselves, produce Jai-class compilation, comfortable
inference, or consistently strong application performance.

After comparison with the newer audit and roadmap revision, the remaining
additions are concrete common-array inference failures, measured type-algebra
growth, generic-instance lookup costs, small-function code-generation costs,
and a source-inspected lazy-string capacity hazard. Local representation
planning, dense aggregate arrays, variant reuse, and the largest-descendant
layout concern were already identified. Those parts of this report corroborate
the earlier work rather than discover new architectural priorities. I still
recommend bringing a narrow semantic-feedback path forward from Phase 5.

## Scope and confidence

I reviewed the language goals, reference, semantic design notes, roadmap, Phase 1
proposals and progress, bootstrap architecture, hosted and native checking,
type algebra, inference, lowering, runtime layouts, string implementation,
direct code generation, command caches, and validation infrastructure. I compared
the findings initially with the September 20, 27, and 29 reviews in the main
checkout. A subsequent review also covered the separate September 29 audit
and the September 30 follow-up on `docs/audit-local-specialization-2026-09-30`,
commit `22346c2a1495`. That material was absent from the main checkout, and I
missed it in the initial comparison. The baseline checkout was
`7dcf76726b23`; development continued in the working tree throughout the audit.
This is an architectural audit with small executable probes, not a whole-compiler
correctness certification or a new performance baseline.

Resource use was deliberately limited: source inspection and short, sequential,
low-priority Python probes, without building a compiler generation or running
pytest. One tiny CLI compilation in an isolated temporary directory was stopped
at its 12-second timeout; I did not pursue an expensive cold prelude build.
There are no new wall-time comparisons with Jai, C, Rust, or previous Dewy builds.
The measured counts and layouts below are useful independently of machine load.

Hosted execution confirms the inference, normalization, layout, cache-decision,
and instruction-output observations. Corresponding native source was inspected;
there was no fresh native build to execute these cases. The large-string issue
is explicitly an inspection finding, not an experiment allocating a huge string.
Compiler and library sources were left untouched by this audit.

The focused second pass below adds native checking/execution through an existing
compiler built from `4870a21a`. Its results have a separate baseline and scope;
they do not retroactively make every original inspection finding a native test.

## What the language is trying to accomplish

The target is unusually ambitious: small, expressive programs with the safety
and predictable ownership of a systems language, engineering-oriented numerics,
and a development loop comfortable enough to use like a scripting language.

- Ordinary assignment, arguments, and returns preserve independent value
  meaning. Inference should arrange borrows, moves, placement, and cleanup
  without making programmers write an ownership protocol everywhere. `@`
  makes deliberate mutation through a place explicit.
- Safety comes from facts and checked contracts. Bounds and dangerous
  operations must be proven safe or have explicit alternatives. Expected
  failures are ordinary union alternatives; effects describe evaluation
  behavior separately. Resource exhaustion remains an acknowledged open design.
- Types combine structural records, nominal families, unions, intersections,
  refinements, and compile-time values. Generic specialization should make
  abstractions efficient while requiring few routine annotations.
- Engineering code should retain dimensions, useful exact numeric defaults,
  and eventually IEEE arithmetic, shapes, broadcasting, linear algebra, and
  efficient CPU/GPU execution. Unicode text means grapheme clusters, with
  explicit lower-level access.
- The compiler should rebuild whole programs without incremental state or
  persistent compiler caches, including the checked prelude. Existing prelude
  caching is transitional; reuse within an invocation and identified test-driver
  artifacts are separate implementation tools.
  Thirty- and ten-second self-builds are intermediate milestones toward
  Jai-class compilation. Ordinary development output should approach optimized
  systems-language performance, not require a slow optimizing build to be useful.

These goals are compatible for a useful, bounded common case. They cannot be
unconditional guarantees for arbitrary Boolean types, unrestricted static
computation, unlimited specialization, or intrinsically expensive exact
arithmetic. The design needs to say where that common case ends and make crossing
the boundary understandable.

## What is working well

The project has made substantial progress beyond a syntax prototype. Native
self-hosting, independently implemented hosted checking/lowering, direct object
output, explicit expected-result tests, and fixed-point checks form a credible
engineering foundation. Keeping the hosted compiler during rapid semantic change
is justified; equality between compiler generations is not a correctness oracle.

The native type arena separates structural shape from declaration metadata.
That is the right distinction: assignment compatibility cannot authorize
forgetting method bodies, defaults, lifecycle operations, or proof provenance.
The problem identified below is excessive work around those identities, not the
existence of the distinction.

Ownership analysis now understands many real compositions: selected fields,
partial transfers, effectful argument evaluation, owner replacement, and cleanup.
The recent equality repairs demonstrate why value semantics need those analyses.
Their cost should be reduced while preserving their meaning.

Finite proof vocabulary, dependency worklists, and unknown on exhausted proof
budgets are sound foundations. Checked library contracts and erased proof calls
offer a more scalable route to ergonomic safety than repeatedly looking through
every implementation at every call.

Scalar arrays and record fields already respect narrow widths and alignment.
The layout concern below is specifically aggregate elements and nominal family
storage; it is not a claim that every scalar occupies a 64-bit slot.

The latest release workflow now waits for successful testing of the exact
revision. I would not repeat the September 29 finding about independently
publishing untested revisions as though it were still unchanged. Similarly,
parser ambiguity, allocation churn, copy-report completeness, unsafe provenance,
resource exhaustion, closures, and absent IEEE/matrix support have already been
identified. They are not presented here as discoveries.

## 1. Inference and specialization need separate policies for facts, semantic instances, and generated code

*Confirmed ergonomic gap and additional scaling evidence. Local specialization
and variant reuse are already accepted in the newer roadmap; these probes identify
specific inference and instance-lookup work within that direction.*

A small hosted probe defines `identity = <T>(x:T):>T => x`, then calls it with
arrays of lengths 1, 2, 3, and 1. It creates three instances. The fourth call
reuses the first, so ordinary instance caching works. What remains is the exact
length distinction inside the type argument.

Another probe demonstrates the annotation burden directly:

```dewy
choose = <T>(a:T b:T):>T => a

let x = choose([1] [2 3])                 # no matching method
let y:array<int64> = choose([1] [2 3])     # accepted
```

Both inputs can be passed as ordinary integer arrays. Without contextual help,
inference does not discover that common array type. The annotation supplies it.
This is an acceptance/inference limitation, not a miscompilation.

The implementation explains the behavior. `TypeSystem.infer_type_args` strips
outer scalar refinements, then binds variables using equality, selected literal
widenings, and numeric promotion. It does not generally find a useful structural
common type for two array arguments. Generic widening retains array lengths.
The native checker likewise preserves nested storage contracts and keys instance
reuse by exact arena identities and effect arguments.

There are two further work-amplification problems:

- Native `instantiate_call` scans the entire registry of generic instances to
  find a matching instance. With growing instance counts this can perform
  quadratic discovery work, including visits to unrelated generics.
- Hosted `_instantiation_key` renders type arguments with `repr`. A shared
  type graph of depth 10, containing only 21 distinct record/array nodes,
  produces a 462,554-byte representation. The outer record occupies only 16
  bytes: its fields are array handles. This expansion is not required by an
  exponentially large runtime record. The compact native shape machinery
  already avoids this particular representation problem.

Adding generics and reflection to library containers increases all of these
pressures. Exact lengths, effect rows, structural arguments, and nested generic
calls can multiply instances without much additional user source. Merely adding
more inference rules can make compilation slower unless instance identity and
code-sharing policy are designed alongside them.

The necessary distinction is:

| Identity | What it must retain |
| --- | --- |
| Source/semantic instance | Defaults, selected methods, lifecycle behavior, invariant storage contracts, and obligations needed to check the body |
| Call-site facts | Exact lengths, value refinements, and facts useful to this caller |
| Generated-code variant | Representation and behavior distinctions actually used by the compiled body |

These identities sometimes coincide, but they should not have to coincide.
Two differently checked instances can potentially share machine code; two
structurally equal types with different selected methods may need different code.
Sharing by layout alone would be unsound. Erasing nested invariants to obtain
more cache hits would also be unsound.

I recommend a per-generic indexed instance lookup, compact retained IDs for
hosted keys, and an explicit inference policy for safe common array/record
types. Follow with dependency-based specialization: retain a fact in the
checked contract, but specialize code on it only when it changes operations,
representation, or a useful optimization. Measure body checks and emitted
variants separately. Add corpus gates for annotation burden, instance count,
and code size, not just whether an example compiles.

As unannotated functions become more capable, collect reusable requirements
from their bodies and solve local constraints using argument and expected-result
types. An overloaded operation may remain a requirement until a concrete call
selects it. This can avoid redoing the entire syntactic body for each transient
fact combination. Dewy's overloads, subtyping, and effects do not automatically
provide a unique principal type: the language needs a deterministic inference
policy and a clear boundary where an ambiguous interface requires an annotation.
The goal is useful inference over small contracts, not unrestricted global
search for a typing of the whole program.

Evidence: `semantic/check.py:7514`, `semantic/check.py:7526`,
`semantic/ty.py:2178`, `bootstrap/semantic/check.dewy:5270`, and
`bootstrap/semantic/check.dewy:5303`.

## 2. The proof budgets do not bound the compiler's type-algebra and specialization work

*Additional evidence: an exponential type-normalization path. Growing generic
recursion was already reproduced by the newer audit. Automatic compiler-query
budgets and programmer-written compile-time execution have different policies.*

Both type algebras eagerly distribute intersections of unions into disjunctive
normal form. Each binary choice doubles the number of clauses. Emptiness checks
receive the fully expanded result before they prune clauses.

The bounded hosted kernel produced:

| Binary choices | DNF clauses | Literal entries |
| ---: | ---: | ---: |
| 6 | 64 | 384 |
| 10 | 1,024 | 10,240 |
| 14 | 16,384 | 229,376 |

This is reachable from accepted source, not just a synthetic private API. A
type alias containing four or eight intersections of binary record unions,
used in a parameter followed by `item is? int64`, causes maximum intermediate
clause counts of 16 and 256 respectively. The function need not be called to
incur that checking work. The probes stop at small sizes.

There is also no useful specialization-cycle boundary for this source:

```dewy
grow = <T>(x:T):>int64 => grow([x])
main = ():>int64 => grow(1)
```

The runtime function is allowed to recurse. Its static instances grow from an
integer to an array of integers, then an array of arrays, and so on. In the
probe, deliberately lowering Python's recursion limit to 220 contained the
experiment; after 23 instance requests it produced `RecursionError`, rather than
a specialization diagnostic. That count is a harness limit, not a language limit
or a measurement of the default compiler's stack capacity. Native source has
the corresponding eager recursive instance construction; native failure behavior
was not executed.

These are exactly the kinds of inputs that undermine a whole-program,
no-incremental-cache compile-speed goal. Cache hits cannot rescue a single
enormous expansion, and better allocation cannot make exponential output cheap.
Compile-time *termination* would not solve this either: a terminating static
program can request enormous work or output.

Use compact Boolean type expressions and prune or answer simple subtype/
disjointness questions before distributing. Lazy clause exploration with early
contradiction checks is a possible intermediate improvement; a particular solver
rewrite is not mandated by this finding. Bound automatic normalization and solver/
optimizer searches, with exhaustion producing unknown or an honest complexity
diagnostic, never an assumed subtype relationship.

The newer policy deliberately permits programmer-written general compile-time
code to run indefinitely. I withdraw the initial recommendation for mandatory
specialization depth/count or general static-execution budgets. Growing instances
need useful traces, cancellation, progress and recovery; optional tooling limits
can contain an experiment without becoming language requirements. Improving that
failure mode is already recorded work. It does not require proving termination
or accepting infinite specialization.

Measure separate scaling axes: type formula size, nesting, overload count,
generic instances, effect vocabulary, and control-flow joins. A source-line
benchmark and a finite numeric-proof budget do not cover these axes.

Evidence: `semantic/ty.py:2085`, `semantic/ty.py:2767`,
`semantic/ty.py:2794`, `bootstrap/semantic/ty.dewy` (`distribute`, `dnf`),
and both generic instantiation paths.

## 3. Ordinary arrays of records need a dense representation before performance can be first class

*Already captured by the newer audit and roadmap. The representation and byte
counts below independently corroborate it; performance consequences are
architectural inference, not a newly timed application benchmark.*

An array element that is a record uses an eight-byte handle. The record lives
in a separate storage block. Release walks the array, loads each handle, releases
its fields, and releases its block. Ordinary scalar arrays are contiguous; arrays
of scalar records are not contiguous records.

For an unbranded `[x:int64 y:int64]`, the record payload is 16 bytes while its
array slot is another 8 bytes. That is 24 logical storage bytes per element before
allocator overhead, compared with 16 for contiguous records. It also introduces
per-element storage management and a dependent pointer load during traversal.
An arena may make those operations cheaper; it does not remove their count or
turn pointer traversal into a dense stream.

This affects game entities, geometry, tabular data, compiler nodes, and ordinary
application records. It limits locality and vectorization even after every
avoidable *value copy* has been removed. Compiling the same pointer graph through
C will not, in general, recover a contiguous array representation.

The newer roadmap explicitly calls for dense aggregate-array criteria and a
homogeneous-array acceptance kernel. This report agrees with that direction.
The remaining implementation question is how early the first useful dense form
can land alongside the throughput campaign; full matrix programming or concurrency
need not precede it.

Start with dense unbranded fixed-layout scalar records. Preserve source value
meaning, and use the existing nonescaping place rules to control loans while
storage moves or grows. Support scalar replacement and bulk initialization/
copying/release for those arrays. More difficult heterogeneous nominal families,
recursive values, and resource-bearing records can follow separately. Stable
address handles should remain available where actually needed.

The valuable invariant is one semantic owner, not one allocation per semantic
element. A dense representation would help the compiler as a Dewy application
as well as its future users.

Evidence: `bootstrap/backend/udewy/layouts.dewy:53`,
`backend/udewy/lowering_arrays.py` (`_array_element_layout`,
`_release_object_elements`), and `tests/python_misc/test_bootstrap_layouts.py`.

## 4. Largest-descendant storage corroborates an already recorded concern

*Already identified in the newer audit, with essentially the same conclusion.
The accepted roadmap reviews this as a general boundary representation while
keeping proven exact locals compact. My original novelty claim was incorrect.*

The reference explicitly says a parent-typed slot is sized for its largest
child. Layout computation also enlarges an unbranded structure that carries
values from a minted family.

A layout probe gives a concrete example:

| Stored type | Small child only | Also declare a child with 128 extra int64 fields |
| --- | ---: | ---: |
| Parent with one int64 field | 16 bytes | 1,040 bytes |
| The small concrete child | 16 bytes | 16 bytes |
| Matching unbranded one-field structure | 16 bytes | 1,040 bytes |

The large child need not be instantiated to participate in the layout registry.
This makes storage cost nonlocal: adding a subtype or an otherwise unrelated
mint changes the size of existing parent and structural values. A wrapper that
accepts the parent can encounter a much larger representation than code using
the concrete child directly. Scalarizing small records is harder, copying parent
values gets more expensive, and future ABI/layout capabilities have to explain
whole-program dependence.

Closed-world exhaustiveness is a defensible language choice. It does not require
largest-descendant physical storage everywhere. Value semantics likewise require
preserving a child's complete value, not reserving maximum family space for every
use of its parent or an unbranded carrier.

Separate exact concrete allocation size from polymorphic-slot representation.
Use a deliberate tagged payload/handle representation where dynamic extent is
needed; reserve maximum-sized inline storage for a chosen closed sum or a proved
small family. Preserve common field offsets and brand-aware operations without
letting all descendants determine all ordinary storage. Establish which layouts
are stable across imported code and which deliberately depend on the whole
program before exposing them through FFI and layout reflection.

This representation question is already part of planned work. The larger probe
quantifies its possible severity; it is not a newly discovered disagreement with
the latest direction. A maximum-sized form can remain useful at a genuine
polymorphic boundary while exact local values use compact representations.

Evidence: `site/reference/src/types-and-conversions.md:31`,
`backend/udewy/lowering_objects.py` (`_object_layout`), and
`bootstrap/backend/udewy/layouts.dewy:154`.

## 5. The development backend needs an optimization boundary before word-and-pointer lowering

*Additional small-function code-generation evidence. Shared representation
planning before raw loads/stores is already specified by the newer follow-up;
that architectural direction is not new here.*

The direct backend is a useful bootstrap tool, but its operation stream is
primarily scalar words, raw loads/stores, calls, and structured control flow.
Aggregate representation and much source-level information have already been
committed by that point. Recording those operations in UBC2 makes transmission
cheaper; it does not restore aggregate identity, useful alias/ownership evidence,
or a high-level array computation.

The current x86 backend also pays substantial costs on very small functions. A
backend probe emitting an identity function produces 19 instructions, reserves
a 48-byte frame, and saves/restores all five callee-saved registers, although
only one is used for the parameter. An ordinary identity can be implemented
with a register move and a return. Native x86 source contains the same unconditional
save/restore strategy. The register allocator is real and useful, but on x86 it
has only two callee-preserved local registers for intervals spanning calls;
three more preserved registers are dedicated to the expression cache.

This matters because small helpers are essential to ergonomic libraries and are
common in the compiler. Explicitly specializing a generic function does not
automatically inline its small body or remove its calling convention costs.

First address inexpensive backend improvements: save only used registers,
provide a small leaf-function path, improve register use across calls, and retain
accurate stack accounting. Then introduce a bounded per-function optimization
step while calls, aggregates, effects, and representation evidence remain
available. Useful customers are small-helper inlining, scalar replacement,
dead stores, redundant field loads, and simple loop transformations. Numerical
fusion/vectorization can grow from that boundary later.

This need not mean requiring LLVM, adding another text serialization, or
building an expensive optimizer before doing any useful work. It means avoiding
an irreversible lowering boundary that forces every subsequent optimization to
reconstruct lost facts from raw addresses. LLVM's own vectorization documentation
illustrates why memory-dependence information matters to optimized loops.
[LLVM vectorization documentation](https://llvm.org/docs/Vectorizers.html)

The earlier September 29 audit correctly warned against adding a new representation
just to remove small serialization costs. The newer follow-up already supplies
the stronger reason for preserving representation and ownership information
before raw loads/stores. This report adds a concrete leaf-call cost to assess
within that existing performance campaign.

Evidence: `udewy/backend/x86_64.py:461`, `udewy/backend/x86_64.py:524`,
`udewy/backend/common.py:635`, `udewy/bootstrap/backend/x86_64.udewy:1232`,
`udewy/stream.py`, and `backend/udewy/lower.py`.

## 6. Cost transparency must include deferred work and representation capacity, not just copies

*Confirmed lazy string mechanisms; source-inspected capacity hazard. The sharing
mechanism is documented, but these implications need explicit design/acceptance
work.*

Native concatenated strings can be constructed without grapheme boundaries.
The first length query scans the bytes and caches a count. The first indexing,
slicing, or iteration consumer may allocate a boundary table sized at four bytes
for every input byte plus one, then scan and cache it. Subsequent operations can
be cheap. This is a useful optimization, but it puts work on the first consumer
rather than the producer.

A tiny retained slice also retains its backing owner. Normal native string-copy
operations use retention of immutable backing, so copying the logical string
does not necessarily compact its physical backing. A short-lived text operation
can therefore produce a small long-lived value that pins a much larger buffer
and its segmentation metadata.

None of this changes string value meaning, and none is adequately explained by
a count of implicit copies. For predictable game/server latency and bounded
memory, the report needs first-touch scans, metadata allocations, and retained
backing storage as separate dimensions. Public effects currently remain
conservative for unclassified string operations; I am not claiming that these
costs have been proved absent by an accepted `no allocates` contract.

There is also a concrete capacity concern. Boundary offsets are uint32.
`write_boundaries` returns `none` for more than `uint32.max` input bytes.
The native lazy `ensure_segmented_body` allocates its table, calls that helper,
and selects count zero on `none`, then caches the table/count. Lazy string
construction does not impose the corresponding capacity check. Thus a valid
string larger than the offset range can reach an internal failure path intended
as a fallback, with no source-level capacity alternative. Indexing depends on
the resulting offsets; this path needs a correctness repair, not just a speed
measurement. No huge allocation was attempted during the audit.

This is not merely the already-open resource-exhaustion question. Even if enough
memory is available, a selected metadata representation has a fixed capacity.
The language must choose a wider/chunked representation, enforce a meaningful
capacity contract, or expose failure deliberately. It must not silently turn
valid text into a zero-length segmentation result.

Keep grapheme semantics and lazy work where it helps. Add explicit preparation/
materialization and compact-storage capabilities as needed, without prescribing
new syntax here. Gate first-use latency and retained bytes on realistic text
workloads. Ensure every narrow metadata representation has a capacity proof or
an explicit failure path. Before concurrent immutable sharing is implemented,
also account for the interior writes and ownership bookkeeping of these caches;
semantic immutability alone is not a synchronization strategy.

Evidence: `bootstrap/backend/udewy/lower.dewy` (`lazy_strings`,
`ensure_length_body`, `ensure_segmented_body`, `segmented_string`),
`library/unicode/graphemes.dewy:187`, and the `_native_string_copy` helper
mapping to `_native_string_retain` in native lowering.

## 7. Semantic editor feedback and outside-programmer evaluation belong earlier

*Sequencing disagreement with the roadmap, supported by current inference
behavior; the absence of a language server is already documented.*

An inference-heavy language asks programmers to rely on facts they cannot see:
the chosen type, specialization, effect row, failed proof, borrow lifetime, and
reason a value needs independent storage. TextMate coloring cannot expose those
answers. Postponing all semantic feedback until after the major feature phases
risks discovering too late that the combined language is hard to use.

The array inference example above is a small illustration. The caller gets
`no matching method`, while an expected result type makes exactly the same call
work. Another probe accepts an inline bounds guard but rejects extracting it
into a bool-returning helper. The latter issue is already anticipated in
`semantic/idiomatic_facts.md`; I do not count helper-contract inference as a new
finding. It does show why programmer effort must be assessed before a much
richer solver or library surface is complete.

Pull forward a narrow editor/inspection path: machine-readable diagnostics,
inferred-type/effect display, declaration navigation, and explanations of chosen
specializations and missing proofs. It can initially consume batch results; a
full incremental compiler is not required. Incomplete-input recovery and reusable
query boundaries should be designed before they require surgery on a mature
whole-program checker. This does not change the uncached batch-build goal.

Use a handful of real programs as recurring customers: a text/file utility, an
input-validated data transform, a record-array update loop, and a small generic
library. Count the casts, explicit types, repeated guards, copies, and unsafe
assumptions necessary for their natural implementations. Repeat after ordinary
helper extraction and API composition. The existing numerical evaluation plan
is a good customer, but it cannot stand in for all ordinary-program ergonomics.

Bootstrap dogfooding supplies unusually difficult compiler workloads. It also
overrepresents arena IDs, tagged compiler records, and authors already fluent in
the language's internal contracts. Successful self-hosting does not establish
that a regular programmer can comfortably write an ordinary application.

## 8. The hosted executable cache can reuse an artifact for the wrong target

*Confirmed defect in temporary tooling. Secondary priority unless it interferes
with target correctness, current development or reliable measurements. Persistent
compiler caches, including the checked prelude, are intended for retirement.*

`dewy.__main__._build_and_run` chooses an artifact path without the requested
target, then returns or runs it when its modification time is sufficiently new.
The cache-hit decision does not inspect target identity. A unit probe with an
existing artifact sentinel requests x86-64, C, and wasm32 in sequence; all three
choose the same artifact without invoking compilation. No sentinel executable
was actually run, and no cross-target backend was built for this probe.

The invalidation scan also inspects nearby `.dewy` source and compiler/library
source timestamps rather than the exact read set. Imports outside the entry
directory, `$include_bytes` inputs, and changed resolution paths are not covered
by that scan. The checked-prelude cache already has stronger content and
resolution checks that demonstrate the intended discipline.

Prefer removing or bypassing this legacy shortcut in invocations that must
recheck source or compare targets. If current development needs to retain it,
a small target/options guard may be justified. Do not build a permanent
dependency-cache architecture for a path intended to disappear. Target-correct
UBC2 cannot protect a command that returns before reading UBC2.

This is a temporary tooling defect, not a fundamental obstacle to the intended
language. Address it when it directly serves target correctness, certification,
dogfooding or measurements. The newer audit's executable-pickle trust defect is
a separate loading issue while that path remains enabled; removing or disabling
the unsafe loader is also a valid resolution.

Evidence: `__main__.py:119`, `__main__.py:291`, `__main__.py:319`,
`udewy/cache.py`, and the isolated cache-decision probe.

## What getting to the requested ideal will take

I would keep the current ownership/correctness closure work, independent
validation, and the newer roadmap's accepted representation direction. The table
distinguishes additional evidence from implementation of existing priorities:

| Work | Deliverable | Evidence that matters |
| --- | --- | --- |
| Additional correctness/scaling work | Contain automatic type-normalization expansion; investigate and repair the string-capacity fallback | Small source regressions, useful diagnostics, clause counts; a capacity contract or explicit failure path |
| With the existing throughput campaign | Indexed generic instances, compact hosted keys, cheap leaf-call improvements; implement accepted source/proof/code identity separation | Body-check and generated-variant counts, code size, per-function instruction traffic, matched direct-built compiler measurements |
| Existing representation work | Dense scalar record arrays and compact exact locals, with explicit general-family boundaries | Allocation counts, bytes/element, locality-sensitive workloads, correct moves/loans/cleanup, lifecycle payload rules |
| During early Phase 2 | Implement accepted representation planning and bounded optimization; pull forward narrow semantic tooling | Small-helper and record-loop performance, explanations for inference failures, observed annotation burden in ordinary programs |
| Conditional temporary tooling | Bypass or retire the executable-cache shortcut where it obstructs reliable work; useful generic traces/cancellation | Correct target/build provenance, no unexpected stale hits, clean tooling recovery; no mandatory general user-execution budget |
| As numerics/GPU work lands | Reuse the same storage, specialization, and optimization contracts | Efficient CPU baseline, then end-to-end device work; preserved numeric/effect meaning and deliberate representation capacity |

For Jai-comparable compilation, removing work is still essential, as the prior
audit says. The additional normalization evidence shows why internal compiler
work needs attention as source and libraries become more expressive. Track unique
semantic nodes, solver queries, clause visits, generic body checks, and emitted
variants. Attribute repeated work to an identity and dependency. Fast ordinary
compilation should come from small summaries and reuse of equivalent variants,
without persistent compiler caches. This is a common-case performance goal,
not a guarantee that unrestricted programmer-written static computation finishes.

For comfortable inference, aim for useful stable interfaces and local contextual
inference. A library author may need to state a meaningful contract once; callers
should not have to repeatedly repair the same fact losses. Keep refinements that
protect stored values. Avoid conflating those contracts with every transient
fact known about a call. Monomorphization itself has real compile-time and
binary-size costs even in established compilers, so instance/code counts deserve
explicit performance targets. Those targets are not mandatory execution ceilings
for programmer-written compile-time code.
[Rust compiler monomorphization documentation](https://rustc-dev-guide.rust-lang.org/backend/monomorph.html)

For first-class runtime performance, copying is only one axis. Representation
density, allocation *count*, helper-call overhead, retained backing storage,
first-use metadata work, and optimization-visible alias information all matter.
A C-based optimizing path is useful evidence and a practical route for some
workloads, but it cannot generally undo a poor aggregate representation already
chosen by Dewy lowering. The default backend needs enough cheap optimization to
make ordinary abstraction affordable.

The project does not need to abandon value semantics, proofs, Unicode text,
juxtaposition, or compile-time Dewy. It does need to make the costs and boundaries
of those features deliberate. Broad feature completion without these decisions
would produce a powerful language that remains expensive to compile and whose
fastest programs require knowing its implementation too well.

## Additional finding 1 Contextual inference switches off too broadly at generic calls

The earlier common-array example extends into an ordinary refactoring problem.
The monomorphic helper below gives `choose` enough context to use `array<int64>`:

```dewy
let choose=<T>(a:T b:T):>T=>a
length=(x:array<int64> tag:int64):>int64=>x.length
main=():>int64=>length(choose([1] [2 3]) 0)
```

Making only the unrelated tag generic makes the inner call fail:

```dewy
let length=<Tag>(x:array<int64> tag:Tag):>int64=>x.length
```

The array parameter is still explicitly `array<int64>`. Its context does not
depend on inferring `Tag`, but the call checker withholds that context anyway.
The hosted checker accepts the monomorphic version and rejects the generic
version; the existing native compiler reproduces the generic rejection at the
inner `choose` call.

The [hosted call checker](semantic/check.py)
passes parameter context only when the sole candidate has no type parameters.
The [native argument checker](bootstrap/semantic/check.dewy)
has the corresponding restriction. This is a concrete implementation obstacle
to ergonomic generic libraries. A useful first fix is to propagate parameter
types already known independently of the unresolved generic variables.

The 18-case hosted matrix exposes two further limits:

| Form | Observed checking behavior |
| --- | --- |
| Typed local, declared return, monomorphic consumer, record constructor field | The direct `choose([1] [2 3])` call accepts with ordinary array context. |
| Typed local containing `identity(choose([1] [2 3]))` | Rejects the inner call even though the outer expected result is an ordinary array. |
| Generic returns `T|none`, `[value:T]` or `array<T>`, with the corresponding expected result annotation | Rejects; contextual binding does not traverse those result constructors. |
| Both input locals annotated `array<int64>` before an uncontextualized call | Still rejects: their current exact lengths are used in inference. |
| A typed intermediate result or a monomorphic helper that hides exact input lengths | Accepts. Annotation location and helper structure affect success. |
| Direct generic moved into a module, or forwarded through a declared generic return | The tested forms accept. Module extraction is not uniformly broken. |

Four of the nested/wrapped-result failures were also reproduced with the native
compiler and the default prelude. Three positive context/intermediate cases
compiled and ran natively with the expected length result. Initial no-prelude
positive cases reached an allocator-related lowering boundary; they are not
counted as successful end-to-end compilations.

This is conservative rejection, not unsafe acceptance. The result changes the
recommended acceptance criteria for inference: count annotations, but also test
whether their position remains useful after wrapping a result, nesting a call,
or making an unrelated parameter generic. Nested expected-result constraints
need a local bidirectional policy, with a clear ambiguity boundary. More
argument-widening rules alone would leave the loss of already-known parameter
context unresolved.

## Additional finding 2 Equivalent code still incurs distinct generic body checks

The following bounded kernel uses two independent type arguments:

```dewy
let probe=<A B>(a:A b:B):>int64=>0
```

Calling it for every pair of array lengths in a small range produces:

| Lengths per argument | Explicit calls | Hosted generic body checks | Hosted emitted functions | Distinct emitted signatures and bodies | Native identical body group |
| ---: | ---: | ---: | ---: | ---: | ---: |
| 3 | 9 | 9 | 9 | 1 | 9 |
| 5 | 25 | 25 | 25 | 1 | Not checked |
| 7 | 49 | 49 | 49 | 1 | 49 |

The hosted functions all lower to `(a:int64 b:int64):>int64` with `return 0`.
The native 9- and 49-instance programs compile and return the independently
expected value 42. Decoding their existing UBC2 artifacts finds identical
two-parameter operation bodies in groups of 9 and 49 respectively; those bodies
only bind the parameters and return zero. This confirmation uses decoded
operations, not symbol-name guesses or a new native build.

Each call appears in the source. This experiment does not demonstrate exponential
growth relative to source size. It demonstrates that independent exact facts
multiply semantic instances and emitted functions even when the body uses none
of those distinctions. The same-type instance reuse in the original probe still
works.

Variant reuse is already accepted roadmap work. This adds a concrete acceptance
kernel and an important completion criterion: deduplicating emitted code leaves
the repeated body checks intact. Measure and reduce elaboration work separately.
A reusable body-requirement/dependency summary can establish which distinctions
need fresh checking; callers must still retain their actual storage contracts
and proof facts. Do not generalize this kernel into sharing by layout alone:
selected operations, ownership protocols, defaults, lifecycle behavior and any
observable function identity remain relevant.

## Representation dependency Append stability relies on the present boxed layout

The new `appends` effect summary is a useful performance improvement. Its
[element stability rule](semantic/analyze/effects.py)
explicitly relies on scalar elements or record handles: growing the array moves
no element record. The lowerer's
[stable-element query](backend/udewy/borrowing.py)
consumes that guarantee without a representation argument.

That is consistent with today's handle-based record arrays. It is not a
representation-independent consequence of append preserving existing values.
An inline dense record array can preserve every element's value while moving
its backing storage and invalidating a retained element address.

The newer roadmap already requires stable-address evidence and dense-array
borrowing rules. This is a concrete implementation dependency within that work,
not a newly discovered general layout problem or a present miscompilation.
Separate semantic element preservation from physical address stability. Borrow
evidence must depend on the selected representation and relevant growth/alias
boundaries. Possible implementations include re-resolving a logical owner/index,
pinning storage, ending the borrow before growth, or using a deliberate value
fallback; this audit does not select one.

Add the same getter/read-across-growth workload to the boxed and future dense
acceptance kernels. The current boxed native case returned the correct value
after 32 appends. A dense form must preserve meaning while choosing an honest
address/borrow strategy; treating dense layout as only a stride change would
leave this existing proof assumption behind.

## What the composition probes established

Six native representation cases returned the independent expected result 42:
parent-typed snapshot, record/none union snapshot, record-array replacement,
nested-field replacement, active optional-array replacement and getter reads
across growth. They exercise brand retention and independent value behavior
through real boundaries. No additional wrong-answer defect was found in these
cases.

Four module/generic programs returned 42 through both compilers: same-named
generics in separate modules, a caller shadowing a private helper, repeated
imports, and namespace imports. These results are positive evidence for lexical
identity and instance separation. They do not cover every import or lifecycle
shape. The lifecycle payload question from the previous audit remains open;
these tests do not impose a new payload-preservation law.

The highest-value additions from this pass are the known-parameter context
failure and the measured duplicate specialization work. The representation
dependency should become an acceptance condition for already-approved dense
storage. The tested ordinary value transitions otherwise provide encouragement
to proceed with the existing design and targeted fixes.

Reproductions, historical observations and binary hashes are preserved in the
[repository probe record](audits/2026-09-30/README.md). The report cites the
inspected baselines; source links navigate the checkout and may have changed
since those observations. The private compiler archive, binaries and caches
are not required to retain the findings and are not committed.

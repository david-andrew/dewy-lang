- **BLUF:** Keep the easy surface, but make cost and progress contracts inspectable and overridable. Dewy's ownership, structured lifetime and level-triggered cancellation are strong foundations; proposal-v2 does not yet establish a complete performance ladder. One keyword can hide scheduling mechanics; it cannot erase admission limits, numerical policy, memory placement or cancellation obligations.
- **Scope:** Brief + proposal-v2 only; primary-source survey checked 2026-11-01. Grades assess the written design, not implementation. Proposal-v2 remains unaccepted; callback safety inference, `Unsent<T>` and `spsc`/`mpmc` are decided. “Best” below means strongest fit for that particular problem, not an overall winner; pitfalls are documented mechanisms, not prevalence statistics.

- **1. Where systems landed**

- **2. Clustered pitfalls; Dewy grade**
- **Function coloring — avoided:** Separate suspendable call protocols infect APIs and higher-order functions. Best avoidance: Go/Loom's ordinary calls. Dewy's inferred effects follow that direction; keep optional restrictions rather than mandatory callback tags.
- **Lifetime and partial cancellation — partly:** Cancellation can interrupt protocol steps, lose resources, or be swallowed; joining can hang. Best baseline: [Trio nurseries, level-triggered cancellation and shielding](https://trio.readthedocs.io/en/v0.32.0/reference-core.html). Dewy adopts these ideas, but cleanup grace expiry and cancellation-safe operations need contracts; interruption cannot undo committed I/O.
- **Numerical reproducibility — partly:** Floating addition is nonassociative; scheduling changes reduction trees. Best avoidance: fixed-order/fixed-tree reduction with explicit numerical policy. Dewy's sequential-order default is strong; “associative proven” needs rules for overflow, NaNs, signed zero and user operators. Deterministic tree ≠ sequential answer.
- **Races and aliasing — avoided within safe code:** Shared mutable aliases cross task boundaries. Best baseline: Rust ownership/`Send`/`Sync`. Dewy's disjoint-place checking and inferred callback safety address this; locks prevent data races, not erroneous protocols.
- **Deadlock and progress — partly:** Bounded executors run consumers before the producer can start; waiting graphs can escape static visibility. Best model distinction: Chapel `forall/coforall`, Zig `async/concurrent`. Dewy's conservative fallback helps finite inputs; certificates need explicit boundaries for opaque calls and external dependencies.
- **False sharing / locality — partly:** Disjoint values still share cache lines; AoS, NUMA and bandwidth limit scaling. Best automation: Futhark's SoA; best control: Halide/ISPC schedules/layout. Dewy mentions `CachePadded`, but padding is not a layout/locality strategy.
- **Nested parallelism / hidden pools — partly:** Each library assumes ownership of all cores; BLAS, task pools and I/O compensation multiply runnable threads. Best baseline: composable Rayon/TBB-style scheduling within one resource domain. Dewy's stolen pool helps internally; foreign pools, quotas and nesting policy remain unspecified.
- **Parallel made slower — partly:** Scheduling, allocations, merges and barriers exceed useful work. Best baseline: adaptive serial cutoffs/chunking, as Futhark documents; PLINQ exposes degree/partition controls. Dewy chunks compute, but specifies neither cost thresholds nor an expert grain override.
- **GIL / foreign escape hatches — partly:** Compatibility locks or opaque native code serialize otherwise parallel work and evade safety assumptions. Best prevention: native safe kernels plus checked FFI contracts. [NumPy demonstrates both GIL release and remaining mutation hazards](https://numpy.org/doc/stable/reference/thread_safety.html); Dewy's unknown-call fallback admits tasks without proving native scalability.
- **SIMD / GPU costs — not addressed:** Divergence, uncoalesced memory, transfers, synchronization and launch overhead dominate. Best ladder: Futhark bulk operations → Halide schedules/Triton kernels. Dewy's “placement context; pool bodies only” states eligibility, not residency, fusion, layout or launch economics.
- **Debugging / reproduction — partly:** Schedule-dependent failures escape ordinary tests; ordered result collection does not order side effects. Best targeted tools: Go race detector, Cilk work/span/race tools, task traces. Dewy's `explain` and model-checked expert primitives help; seeded select randomness does not replay readiness or scheduling.
- **Priority inversion / responsiveness — not addressed:** Urgent tasks wait behind low-priority dependencies or long compute. Best baseline: [Swift dependency-driven priority escalation](https://developer.apple.com/documentation/swift/task/escalatepriority(to:)). Dewy promises preemption/safepoints but no donation, fairness or latency contract; random selection gives no bounded starvation guarantee.
- **Blocking inside async runtimes — partly:** Blocking monopolizes a carrier; compensation can merely replace starvation with oversubscription. Best baseline: Loom's runtime-integrated blocking, explicit FFI isolation. [Tokio's mutex guidance](https://tokio.rs/tokio/tutorial/shared-state) illustrates the hazard. Dewy's runtime duties acknowledge it, but “non-parking log write stays pooled” can still stall a worker.

- **3. Beyond concurrency: an 80/20 structure**
- **Python/NumPy:** Make bulk work idiomatic before asking users to manage threads: tensors, broadcasting, scans, reductions and batched I/O. Preserve that expression as it gains a native implementation; avoid forcing the expert to rewrite the algorithm in another language. NumPy's vectorization alone does not promise multicore execution.
- **Rust:** Opt-in power should cross a small, named obligation boundary and return behind a safe abstraction. `unsafe` does not disable the whole checker. Dewy's danger/atomic/FFI APIs should expose particular assumptions, not a global “trust me” performance mode. [Safe abstractions over unsafe internals](https://doc.rust-lang.org/book/ch20-01-unsafe-rust.html).
- **Swift:** Progressive disclosure works when default inference and explicit isolation/executor controls describe the same model. Hidden inference still needs stable explanations and optional constraints; removing written `async` does not remove programmer obligations around waiting, reentrancy and cancellation.
- **Julia:** Multiple dispatch lets generic array code acquire specialized CPU/GPU implementations without changing its caller. Pair specialization with understandable dispatch, layout and allocation diagnostics; open extension must not make performance depend on mysterious combinations of methods.
- **Halide:** Separate what is computed from how it runs. Dewy can keep `[parallel x in xs f(x)]` while refining placement, layout and chunk policy. These are independent axes, not reasons to accumulate synonymous loop forms.
- **C++/Scala caution — design inference:** Complexity accumulates when new escape hatches interact with templates/implicits, overloads, ownership and multiple executor/future ecosystems. The failure mode is combinatorial reasoning, not expressiveness itself. Require orthogonal controls, one scope/error model, and documented interaction rules; delete redundant constructs before release.

- **4. Top five gaps, in priority order**
- **1 — Admission and progress contract:** Prove when bounded execution preserves progress; expose a resource limit with a diagnostic when incompatible. `parallel i in [0..n) step(ch i)` cannot both guarantee arbitrary sibling rendezvous and promise bounded task memory. Receiver loops always windowing also conflicts with bodies waiting on future items. Shared mutex use alone should not force millions of tasks. Knob spellings remain David's decision.
- **2 — Stable cancellation semantics:** C4 makes cancellation depend on whether the enclosing result already includes `Canceled`; clarify inference without circularity. Compare `heavy` with/without that result arm under `within(1ms @heavy(xs))`: a deadline may wait far beyond 1ms while joining. Define grace-expiry behavior without detaching borrowed children, safe cleanup, and `select` payload ownership on losing sends.
- **3 — Hardware ladder:** Specify ordinary tensor fusion/vectorization → multicore → resident GPU arrays → custom kernels, with common layouts and explicit transfer/synchronization boundaries. Start with `let squares = [parallel x in xs x*x]`; explain whether it vectorized, allocated an intermediate, fused with `sum`, or copied devices. Do not imply all pool-safe bodies are device-compilable.
- **4 — Composable resource and performance controls:** Give nested scopes a shared CPU budget; define foreign BLAS interaction, chunk thresholds, layout/NUMA controls, blocking compensation limits and priority behavior. Keep `frame ... & no blocks` as a checked restriction, but reconcile broad `blocks` with the narrower `may park` strategy classifier; it currently does not describe the same guarantee.
- **5 — Actionable tooling:** Extend `explain` from “chosen strategy” to forcing call, task/memory estimate, cutoff, fusion/vectorization rejection, transfer bytes and runtime attribution. Add task/wait traces, race checks and schedule exploration/replay. Protect compile speed with bounded, demand-driven dependency analysis; unknown information must produce an honest cost warning, not optimistic independence.

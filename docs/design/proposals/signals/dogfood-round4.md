# Round 4 dogfood

Final specification: round4.md. All 32 scenario files and three support modules are in programs-r4/. This is a self-contained revised suite; 10, 13 and support/search are retained unchanged. Programs 16, 26 and 27 are explicitly unsupported/counterexample fixtures, not working examples of a promised capability. Earlier sources and dogfood remain unchanged.

These are paper programs. I read both independent reviews in full, traced the revised lifecycle/output/failure paths, and checked local imports and surface conventions. I did not run native signal programs, compile proposed library features, benchmark a runtime, or cold-read names. The old closure_model.py is not validation of round4: its manually labeled dependency states, independent join classifier and historical view map do not implement the new rules. Round4 section 6 instead gives ten explicit boundary traces, including every S4 case.

## Scores and every sub-5 deduction

O = obvious; D = discoverable; C = concise; S = safe by default; F = complete for its stated task. Each is 1–5. A 5 is a design judgment with no material deduction found, not executable evidence. The numbered references below are **actual lines in programs-r4/**. Support-module references are relative to that directory. Every dimension below 5 is named with its own reason and location; combined O/D reasons apply to both dimensions explicitly.

For 16, F2 means the proposed reactive extension is unsupported. For 26/27, F2 measures the desired eventual-shutdown behavior that the counterexamples deliberately fail. Their static traces are useful precisely because that behavior is not promised. Do not mix those expected failures into a claim that (b) now guarantees liveness, or omit them to manufacture a universal floor.

## Five-language comparison for every keyed row

This keeps the independent regrade's useful comparison method. Every row above uses at least one key; each key compares against **all five** languages. These are conceptual idiom comparisons, not new language feature research or executable peer suites. The primary references and their limitations are recorded in dogfood.md; the design claims here concern the written Dewy programs.

| Key | Python | Go | Rust/Tokio | TypeScript/Node | Swift/Dispatch |
|---|---|---|---|---|---|
| E: events/lifetime | Signal handler or async adapter plus explicit task lifetime | Signal channels and stop/done/wait ownership | Signal streams, selects and owned task lifetime | Event subscriptions plus explicit removal/abort/join | Dispatch source/AsyncSequence adaptation plus cancellation lifetime |
| R: input/output ordering | Short synchronous KeyboardInterrupt loop; separate printer needs coordination | Console reader plus signal channel and ordered message/ack | Line editor plus signal selection; single output owner or channels | Readline/process events; callbacks must serialize prompt/output | Console adapter plus signal source; actor or channel coordinates output |
| G: graceful work | Cancel/join, finally and cancellation-aware protected cleanup | Context cancellation, independent save deadline and wait group | Cooperative cancellation, owned resources and deadline scope | Abort plus explicit completion/cleanup promises | Structured task cancellation and owned cleanup |
| P: platform | Native terminal/process/console limits still apply | Native limits; explicit platform APIs | Native limits; platform crates/adapters | Host-specific process/console behavior | Native limits; Unix Dispatch is not a Windows close API |
| N: ordinary work | Default interrupt policy, no custom listener | Default native policy, no listener | Default native policy, no listener | Host default policy, no listener | Host default policy, no listener |

Round4 E now removes the required acquisition/release pair from the common path. It does not claim ownership of the general idea of signals as event streams: Go channels and Rust/Swift streams already offer related compositions. Dewy's automatic quiescent closure is its extra rule, and the 3s for discoverability remain honest. R keeps Python's straightforward prompt-only exception loop as a shorter benchmark; requiring a separately executing printer costs explicit coordination in all five comparators as well. G retains cooperative limits rather than claiming to save through forced process death. P limits are not reasons to add new signal syntax.

## Acceptance and floor

- The selected design no longer depends on remembering signal cleanup, and a descriptor escaping into another task cannot retain an old subscription. Actual waits in that task can intentionally attach its own scope; merely holding the value cannot.
- All shutdown samples now distinguish unsuccessful closure/facility loss from successful shutdown. The multi-source example drains normal closure and documents fail-fast error behavior.
- Prompt ordering is a written protocol, not a scheduler guess. The simple raw parallel printer is not presented as an ordered REPL.
- Mixed timers and overlapping handlers remain real counterexamples to eventual shutdown; both are next to the main idiom and have existing-construct remedies.
- Names remain provisional. Automatic owners, retirement, native epochs and terminal reset require implementation/testing; the old model is not proof of them.

**Selected working-design floor: 3**, from contextual lifetime discoverability, ordered-REPL/barrier verbosity, and platform completeness. **Unsupported/negative fixture floor: 2**, explicitly program 16 (unimplemented guard semantics) and programs 26/27 (no eventual-shutdown guarantee under their schedules). There is no remaining claimed safety-2 escaped-registration case. That distinction does not inflate the current examples to all 5s or hide the fact that choosing (b) accepts a nontrivial lifetime rule.

# Independent regrade of signals, round 3

Read brief.md, round3.md, summary.md, all 23 programs and all three support modules, plus relevant LANGUAGE.md and decisions.md passages. I did not read dogfood.md before writing these grades (and have not read it afterward). Repository remained read-only. Owned output: this report and programs-regrade/ only. Non-goals: implementation, new syntax, benchmarking, renaming, or editing the author's design. Budget: one bounded review session. Acceptance: three independent edge programs, every supplied program graded, concrete reasons for every deduction, and actionable findings.

**Floor: 2/5** for safety in the omitted-cleanup/escaped-registration case; **3/5 for discoverability of the selected normal model**. This is not a claim that normal examples all fail. The basic parallel iterator is attractive, and explicit acquisition prevents scheduler-dependent interception. The contextual lifetime rules and ownership fallback fall short of a gold-standard 5. Platform limits are separate from fixable design costs.

These are static design grades, not compiler results. Current LANGUAGE.md still describes an older implemented concurrency surface; I assessed the proposal against its stated accepted future dependencies, not by pretending these files compile today. I did not make external-platform verification claims.

## Independent programs

- programs-regrade/01_owner_repl.dewy: closest working version of David's record/parallel sketch, with real input error handling, EOF and quit.
- programs-regrade/02_drain_server.dewy: two concurrent request lanes, accepting until SIGTERM; race cancels and joins both lanes, protected accepted requests finish or time out, sockets close, then main returns. Five seconds is a cooperative upper bound on remaining per-request budgets, not a fresh five-second grace starting at SIGTERM. Concurrent accept on a shared listener and cancellation-safe I/O are assumed library capabilities; neither is demonstrated by executable evidence here.
- programs-regrade/03_forgotten_lifetime.dewy: deliberately invalid acquisition case and two cleanup cases. These are isolated negative fixtures in one file, not one runnable executable: line 5 prevents compiling the complete file. Without acquisition, the promised error is compile-time. Without defer and without escaping copies, last-drop fallback works. Without defer but with a background copy, default Ctrl-C remains suppressed and program-group joining can wait indefinitely. These cases must not be conflated.

## Comparison basis

Scores are O=obvious, D=discoverable, C=concise, S=safe by default, F=complete for the stated scenario, each 1–5. A 5 means no material design friction found, not proof of implementation. Every score below 5 has a dimension-specific line reason below. Locations without a directory mean programs/. M marks machinery beyond David's sketch; not all M lines are unjustified. Imports and ordinary error propagation are not automatically counted as gratuitous machinery.

The following comparison keys apply to each row using that key, against **all five** languages. These are conceptual comparisons, not claims of tested implementations or exact syntax parity:

| Key | Python | Go | Rust | TypeScript | Swift |

| E: event listeners | Async event handling needs installation/removal and task lifetime | Signal channels plus explicit stop/cancellation | Stream ownership and explicit task/select lifetime | Event subscription/removal and async task lifetime | Dispatch/async source and explicit cancellation lifetime |
| R: REPL | Input interruption has a familiar direct exception path | Console editing and signal coordination require libraries | Console editing plus signal stream coordination | Readline and process events must be coordinated | Console editing and signal source require explicit coordination |
| G: graceful work/cleanup | Finally/task cancellation and bounded async cleanup | Context/deadline and joins | Ownership/select plus cancellation-safe cleanup | Abort/lifecycle and promise cleanup | Structured cancellation and resource cleanup |
| P: platform | OS-specific constraints still apply | OS-specific constraints still apply | OS-specific constraints still apply | OS-specific constraints still apply | OS-specific constraints still apply |
| N: ordinary work | No signal setup required | No signal setup required | No signal setup required | No signal setup required | No signal setup required |

Dewy E is shorter than explicit event-plus-done plumbing in these comparators, but its source changes termination and fan-out with ambient parallel ownership. R gains the desired parallel shape but still duplicates interruption handling. G retains the familiar cooperative-deadline limitation; the proposal should not be penalized merely because it cannot guarantee saving through forced process death. P deductions are scope limitations, not demands to overcome the OS. Rust-style explicit ownership would make an escaped cancellation authority easier to identify; none of the other comparators gets automatic credit for handling leaked subscriptions safely.

## Must-fix before claiming the requested ergonomic floor

1. **Multi-handler shutdown has no bounded backlog at the block level.** round3 L89,L110,L121–125; extend 08_busy_handler L6–10 with a second independent observer doing a differently timed slow handler. After finite work ends, A is processing while B registers its next signal wait, and B is processing while A registers its next wait. A stream spaced more than one second apart avoids the emergency rule yet replenishes both mailboxes. The closure predicate is never true. Example schedule: A and B both start handling at t=0; A handles for 2s, B for 3s; notifications arrive at t=1.1,2.2,3.3,...; at t=2 B is busy, at t=3 A is busy, at t=4 B is busy, and at t=6 whichever next registers sees the other ready/running (explicitly ordinary by L91). Repeat. Work can finish at t=0.5 yet handlers run indefinitely. The prose correctly limits backlog *after closure*, but the headline “handler finishes current work then closes” is not compositional. Specify this limitation prominently and dogfood this schedule; either provide a finite intake cutoff policy or explicitly require race/done coordination for eventual shutdown under continuing signals. Do not claim merely “one final event per view” proves shutdown.
2. **Make escaped registration authority safe or explicitly mandatory to manage.** regrade/03 L11–16 and round3 L69,L141. Last-drop is insufficient for a forgotten defer when a background task retains the handle: the task's event wait retains the authority that would keep it alive. Auto-closing a parallel view does not revoke it. Resolve owner versus subscription lifetime, require structured ownership of interception, or provide a concrete diagnostic/lifecycle rule for this case. Existing emergency exit mitigates escape but does not earn safe-by-default 5. This is an ergonomic acceptance problem in a specified rule, not an assertion that the rule is internally contradictory.
3. **Handle unexpected facility closure explicitly in shutdown examples.** 02 L24, 03 L35, 11 L29, 14 L14. The design uses Closed both for successful quiescence and backend loss (round3 L171). Outside parallel, the search/server/editor examples cannot treat Closed as intended completion; report/propagate failure. The multi-source monitor needs an explicit source-retirement or fail policy. No new syntax is needed; the independent server L38 shows the minimal failure path.

## Should-fix / qualification

- 01 L5–10 and support/repl L7–10: explain the dual delivery path in the first REPL example, not only the API chapter. A user's signal handler does not run on the normal prompt-interrupt path. “Signals as events” alone predicts the wrong hook for REPL metrics or cleanup.
- 20 L6,L14–15 and 07 L10–11: include one ready-barrier example if independent view broadcast is a supported use case. Acquisition before work only establishes registration, not attachment of every view.
- round3 L139,L143 and 12 L10: show the tiny refactor from a direct helper to a nested parallel that terminates immediately, and the same helper outside parallel that runs forever. This is a major discoverability cost even though fully specified.
- 14 L14: breaking on the first closed source can leave buffered events on other closed views unprocessed; document whether final reload/dump actions are intentionally discarded.
- 03 L17,L42: distinguish request budget, shutdown grace, and total shutdown time. The final count write adds another two seconds after draining. Do not label this a five-second total shutdown deadline.
- 06 L16–18: printing dimensions is weaker than making them available to a real layout calculation; track terminal-size support separately. Full shell job control and Windows close limits are honest scope floors, not evidence the core event iterator needs replacement.
- Program16 is an alternative, not a working round3 program; retain that clear labeling. Names are provisional; this review did not cold-read names or approve them.
- None of the grades imply executable validation, native callback correctness, or measured overhead. Those remain implementation gates, not grounds to add evidence artifacts to the repository.

The minimal successful lesson is worth keeping: acquire policy before starting work, use ordinary parallel iteration, close visibly, preserve true cancellation, and make aggressive cancellation an explicit race. The unresolved issue is how much contextual lifetime machinery a reader must learn to trust that short form.

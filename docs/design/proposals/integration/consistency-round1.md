# Consistency audit — 2026-11-07

**BLUF:** The pending designs do not yet describe one consistent language. The largest problems are observable semantics: settings that change API result types, unchecked literal-union conversions, interval emptiness on discrete domains, and an exception to multi-expression composition. Several linked proposals also retain names and constructs already superseded by decisions. Reconcile those contracts before asking the owner to approve spellings.

Scope: every open item, the decisions ledger including batches 2–3, all requested proposals, time v6 and its inherited v5 sections, and relevant language/ownership/multi-expression rules. ## Does `( … )` preserve order inside `parallel { … }`?

**Yes for a valid grouped expression, by the proposed rules; it is not a general replacement for a statement block.** C §3 makes each top-level statement one item. M Substitution invariance defines `(a b)` as several values, not a container, and M Effects says every expression evaluates “exactly once, in source order.” Consequently a parenthesized group used as one item evaluates its constituent expressions in order. Flattening its expressed values does not authorize scheduling those expressions as independent items. Nested explicit `parallel` constructs can still introduce parallel work.

**This application to v3 is inferred**, not a claim that the pending scheduler was executed. C should state it and add a regression case alongside the `{ … }` case. Braces remain the documented way to sequence arbitrary statements, introduce bindings and provide a scope. Parentheses group expressions: they do not create that scope or accept an arbitrary `let`/metatag statement list. The current reader's `rt_dc_group` (`compiler/dewy_reader_seed.jo:655`) parses expression groups; `values_group` (`compiler/checker_value_calls.jo:401`) checks them as values.

## Checked distinctions that should not be “fixed” into inconsistencies

- **Ranges:** L explicitly says non-integer `Range<T>` is not iterable; `IntRange` is lazy and iterable. D4's `Iterable<T>` therefore need not accept a date/instant interval. `.first` and `.last` on `Range<T>` are the written bounds, potentially excluded—not necessarily members. The emptiness bug above is separate.
- **Failure operators:** `?? return`, `?? break`, `?? continue` are accepted. `or_throw` forwards exceptions; `?? void` filters them in a collector. `Unsent<T>` retains payload, `ShapeError` explains validation, and `NoEntropy` identifies secure-random failure; these need not be one universal error. `Sent` is a matchable select-success marker, not a reason to change ordinary sends from `void`.
- **Function types:** `()` is idiomatic; `<>` remains valid. D30's bare annotation is an explicitly rejected candidate, not an unexplained conflict. Ordinary `f()` is still permitted by D's standing rule; the newer no-parentheses examples establish style, with the returned-place exception above.
- D32's data-license question, D33's explicit self-reference extension, D35's zoned conversion, and D36's derived dimensions reveal no additional verified cross-design contradiction. Unlimited pure compile-time evaluation and packages' ban on host effects are different policies; `compiler/checked_eval.dewy` already rejects host effects.

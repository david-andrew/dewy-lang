# Contracts used by the paper programs

These are proposed or illustrative APIs, **not files supplied by today's toolchain**. Imports ending in `.dewy` follow batch 7. None of these programs has been compiled or run, and no GUI/audio program is launched. Existing names are reused where their meanings fit. Standard-library additions are distinct from example application APIs below.

## Existing mechanisms relied on

- `$__drop__` is non-failing `void`; owners move at proven last use. Ordinary borrowed calls and place-lending call statements retain their input storage through the call. Partial aggregates, returned owners, once-run task captures and resource arrays already have lifecycle rules.
- `@` arguments are ordinary places; a place parameter cannot escape. A raw field behind an outer hook cannot transfer independently. Unknown calls do not justify an ownership or no-escape proof.
- `parallel` is the accepted batch-3 form, not LANGUAGE.md's obsolete `concurrent`. `task.tasks(@body)` and `group.spawn` are D4's ordinary task APIs. Only the scheduler's already recognized once-run spawn body can move a captured owner onward; ordinary repeatedly callable closures cannot.
- `protect_from_cancel(duration @call)` is an existing D4 library operation. It joins, returns `Timeout` for its own cooperative deadline, and retains the body's errors. A direct outer cancellation still exists after returning from the shield.
- A `void`-context callback may discard values in Dewy. Therefore the APIs below infer a supplied callback's concrete result before selecting/instantiating the wrapper. They do **not** coerce a potentially failing body into `(@resource:File:>void)` and thereby swallow its final failure value. Program 13 states this constraint explicitly.

## Normal completion, abnormal termination and deadlines

The acquisition function is the sole owner of its fallible resource. A body is called once, directly, with a borrowed `@` argument; its result is held until finalization completes. A normal return, a returned failure value and a callback's `or_throw` all reach this ordinary finalization code. The acquisition call returns the body's success value or the combined failure; it never resumes a canceled outer `return` after cleanup fails.

Finalization runs normally first. If its resumable phase runner returns Canceled, continue the remaining state as `protect_from_cancel(100ms @finish(...))`. A scoped acquisition's `timeout=` argument changes **only cancellation-finalization grace**, not normal completion or acquisition/body duration. This is a new application of an existing parameter spelling and must be stated in the signature/hover. For a deadline over the whole operation, wrap the acquisition call in existing `within(...)` instead. This final rule supersedes round 2's always-shielded prototype and avoids an arbitrary deadline on uncanceled file flushes. No one claims a 100 ms total task join: nested acquisitions add their budgets. `timeout=2s` explicitly permits a two-second cooperative grace after cancellation. Non-cooperating foreign calls may overrun.

A completed finalizer preserves phase state, records failures, attempts remaining cleanup, and relinquishes all releasable native ownership before returning its final result. A provisional Canceled status retains the resource in the acquisition wrapper for continuation under grace; it is not the final result or a release of ownership. It does not detach a timed-out cleanup. A close attempt that may already have closed a descriptor is not retried. A task group joins the real finalizer before exposing its result.

Compiler-controlled panic/exit do not ordinarily resume the callback wrapper's sequential epilogue. Their existing owner-unwind dispatcher therefore reaches a non-failing emergency backstop. That path releases what it can and reports meaningful cleanup failures through an emergency diagnostic routine; it does not claim a save/flush succeeded or return a regular success value. An adapter without a verified/trusted backstop cannot implement these safe APIs. This is a material implementation requirement, not proof that every current OS wrapper already meets it. SIGKILL, power loss, foreign faults/longjmp and forced third Ctrl-C cannot guarantee user cleanup. Buffered output may be incomplete on a forced/nonreturning path.

## Error composition (library, not implicit throwing)

`cleanup.CleanupError` is a nominal `error` with `.primary:exception`, `.cleanup:exception` and a fixed safe `.message`. Its fields hold non-`none` failures. No automatic extension of every nominal error's type is required.

- Success + success => exact success.
- Success + cleanup failure => cleanup failure, after destroying any withheld owning success result.
- Body failure + success => exact body failure.
- Body failure + cleanup failure => `CleanupError[primary=body cleanup=finish]`.
- `none` is success. Other exception outcomes count as failure. A record/array containing an error is still a successful value unless its callback explicitly returns/forwards that error.
- Flush failure plus close failure are nested in operation order, and then paired with a failed body if one exists. Cleanup of multiple resources attempts each and folds failures; the first failure is never thrown early in a way that skips subsequent releases.
- A paired cancellation is no longer a bare `Canceled`. The ordinary `CleanupError` is a failure; `.primary` preserves `Canceled`. Explicit handlers, task failure reporting and default main output show that distinction. A cleanup failure during Ctrl-C therefore exits with the cleanup error's code rather than silently preserving 130.
- Runtime/library reports of `CleanupError` recursively print safe kind/message information for the two causes, never full payloads by default. User-created pathological recursive errors must not cause infinite reporting; bound diagnostic depth, state that further causes exist, and keep the full value inspectable.

When completion is canceled, a successful callback outcome is replaced by Canceled before combining with resumed completion; an already failed callback retains its failure. The initial provisional Canceled is not itself paired with the same Canceled body. Actual flush/close errors remain in finalizer state. After any protected continuation joins, collect that ledger plus its boundary outcome (including Timeout), so protection cannot replace a real error recorded before the deadline. Drain/consume the ledger once to avoid duplicating the same failure. Fully finished phase state is idempotent; raw close is not blindly retried. Round3.md's final cancellation correction contains the ordinary-value control flow.

## Standard APIs proposed

### Files

`files.File` is a scoped, move-only internal owner lent to a callback. Safe users cannot receive one from an unscoped fallible writer factory. A wrapper retains ownership and uses the file after the callback, which rules out moving it to a return/global/longer-lived task.

`files.open(path mode @body timeout=100ms)` calls `body(@file)`, then completes the file. Modes used here are `'read'` and `'write'`. The context overload `files.open(path mode @body @context timeout=100ms)` calls `body(@file @context)`, with existing generic `R`/context types. This overload avoids an escaping or generic owner-capturing closure, and needs no new callback marker. Callback bodies can be named functions or direct lambdas whose ordinary summaries prove nonescape.

`file.read_bytes(maximum)` gives `array<uint8> | none | file_errors | Canceled`; maximum must be positive. `none` alone is EOF. `file.write_bytes(bytes)` gives a byte count or file errors/Canceled and accepts the whole offered buffer on success, including into its output buffer. The normal buffered writer has at least 4096 bytes and does not force a flush for the three-byte demonstration in program 01; no persistence/completion success is promised by that intermediate call. Wrapper completion attempts buffered flush and then native close on **every** ordinary outcome; errors from both remain values. It does not promise crash durability unless the API requests sync explicitly. No new public sync option is proposed in this cleanup round. Existing `Path.write_bytes` retains its separately documented atomic/durable replacement guarantee. Existing `Path.copy_to` also reports any copy completion/close failure before returning a successful count.

A read file can still fail on close; the same wrapper policy applies. A filename Path is ordinary copyable text, not a descriptor owner. Standard inputs/outputs are borrowed program services; code that starts an independently buffered writer uses the scoped API. An explicit `printl` remains the existing infallible console operation; this round does not silently change its type or invent hidden main result alternatives. Observing general console/output errors is a separate existing API-policy issue, not solved by changing a file destructor. An explicitly created buffered File writer always uses the scoped completion contract here.

`files.temp_dir(@body timeout=100ms)` creates a unique directory, calls `body(path)` and removes the tree. Its cleanup owns the directory's identity, not just a user-replaceable path string: do not follow replaced symlinks or recursively delete an unrelated tree. A deletion failure identifies the remaining directory in a deliberately diagnostic-safe field/message chosen by that API. The copied Path is not a lifetime-bearing view and may outlive the directory. A temp file is the same pattern, optionally exposed as a borrowed `File` plus a Path; no new spelling for it is standardized here.

A collection of fallible files is held by a scoped application/library owner that finalizes **all** initialized files, then drops raw backstops. It can use the same `open` callback pattern, repeated acquisitions, or an ordinary batch wrapper. This round does not add a universal heterogenous resource stack or file-array constructor. Infallible owners in arrays need no such wrapper.

### Sockets and tickers

Existing `net.tcp_connect/listen/accept` return move-only `TcpStream`/`TcpListener` owners. Existing send/receive functions borrow them. Drop releases the local handle/registration, without waiting for peer acknowledgement or promising application-protocol completion. Native adapters must handle target-specific close behavior without closing the same reused descriptor twice. Standard library `tcp_close` is not required for correctness; it may remain an explicit consuming early-release API only if needed. It is absent from the recommended examples.

`ticker(duration)` returns an owning timer. Drop stops it. An explicit ticker `.stop()` is a consuming early stop, not a required second step; a later use is rejected. Task.stop is different: its observer remains available for wait/error inspection. A wait operation borrowed from a timer keeps it alive through that wait; it cannot be stored after the timer dies.

### Channels

`channel<T>(capacity)` returns `[Sender<T> Receiver<T>]` with the existing bounded wait/outcome rules. `mpmc<T>(capacity)` likewise returns separate endpoint owners and preserves its distinct `Busy` attempt outcome. Implementations may share queue storage; endpoints, not the buffer reference count, count sending/receiving rights.

- `Sender<T>` and `Receiver<T>` are move-only; no implicit copy and no `$__copy__`. Their drop hooks relinquish their capability once. Ordinary task/record/array moves apply.
- A consuming `sender.split` produces two sender owners and increments the sending-right count by one. `receiver.split` does the same for multi-consumer receiving rights. Construction and split have their normal allocation/resource-failure policy; there is no per-send allocation requirement. `spsc` retains its existing distinct endpoint types and cannot split an endpoint.
- Last sender drop ends sending. No separate sender-close method is needed for correctness or proposed in this round. Already admitted buffered payloads remain available. Receive drains them and then returns existing `Closed<T>`. Waiting receivers wake. Dropping one of two sender owners does not prematurely stop the other; it relinquishes that one capability.
- Last receiver drop wakes blocked senders with `Unsent<T>` whose `.value` is the original offered payload and `.reason` is Closed. New sends fail similarly; remaining buffered owners are released in queue order by a documented queue cleanup routine (this is separate from reverse array cleanup).
- A reservation for a guaranteed `permit.send(value)` owns a sending capability too. Dropping the sender cannot close sending while that permit is outstanding. Dropping an unused permit releases that right and capacity. Last-sender closure therefore includes all outstanding permits. A permit retains queue storage through commit; successful commit is acceptance, not a promise that a receiver will eventually process the value. If all receivers disappear, accepted buffered payloads are released during orphan-queue cleanup. This preserves D4's already accepted infallible reserved send without claiming successful delivery.
- A prepared receive/send/select operation only borrows its endpoint, retaining it through the operation. A borrowed wait cannot outlive its endpoint. A queued payload that contains a sender to the **same** queue can form a refcount cycle; apply existing proven-deadlock diagnostics where a cycle is visible, and warn where the existing analysis exposes unresolved identity. This proposal does not add a new general capability-graph cycle solver. No claim that arbitrary cyclic capability graphs are collectable is made.
- A self-retained sender, a task that never reaches its final use, or an intentionally kept producer owner can still keep a channel open. Static known deadlocks are errors; unknown graphs warn as before. Ownership fixes forgotten close, not distributed termination detection.

### Locks

No new API. `@(mutex.lock())` lends the protected data, with its lending method's acquisition guard. A `let` loan ends after the last statement using it; braces alone do not extend it. `operate(@(mutex.lock()))` holds the lock for the whole call statement. This can be a named helper containing arbitrary fallible statements and its own no-fail defers. Helpers must not escape the place or recursively acquire the held mutex. Two-lock operations still need existing `lock_all`, not two independent calls that briefly stop overlapping. No inference from the apparent visual indentation of a brace is assumed.

### Processes

Existing fully owned helpers `run/capture` complete their child lifecycle and return status/errors. A caller that needs interactive child pipes uses a callback overload of existing `files.spawn(program args @body timeout=100ms)`; the wrapper owns the child until callback, pipe completion, stop-if-needed and reap finish. It exposes a borrowed `Child`, not an unscoped raw handle with a silently fallible destructor. Canceling `child.wait` only ends that wait; acquisition still owns the child. A child whose termination/reap cannot complete cooperatively may exceed cleanup grace and is still joined/owned; warn for such waits. An intentional process that outlives its launching operation is a separate explicit supervisor API, not a leaking drop convention.

### Terminal mode

`terminal.raw(@body signals=true timeout=100ms)` saves the exact terminal settings, installs byte-oriented input and restores on every ordinary callback outcome. `signals=true` retains OS terminal signal generation (ISIG on POSIX); fully raw mode with it off delivers Ctrl-C as input byte 3 and cannot be described as default SIGINT cancellation. `Terminal.read_bytes/write_bytes` follow File's result conventions. The raw helper restores partially changed settings if acquisition fails, combining that failure with a failed restoration. Saved modes form a lexical stack, so nested sessions restore their immediate predecessor. This operation is task-affine and cannot move into unrelated tasks. Multiple simultaneous mode owners for the same terminal must be rejected or serialized; printing does not silently change terminal mode.

## Illustrative application APIs (not proposed as new std modules)

`game_assets.dewy` supplies `Texture`, `Sound`, `load_texture(path)`, `load_sound(path)` and `run(@level)`. Loaders return their owner or an ordinary error; they reserve bookkeeping needed for allocation-free release. A failed Level construction drops completed assets. GPU submissions own in-flight references; the drop retires the public owner and safe native destruction waits for its fence. Queue/driver waits and possible retained memory get a performance warning. Playback owns its loaded samples separately; dropping a `PlayingSound` observer does not stop one-shot audio (D11). A game engine retaining assets through callbacks must have a real owning state object or a checked borrowed call, as in program 08; an unused setup-local or module-global owner is not assumed to live across frames. Global owners are currently unsupported.

`db.dewy` supplies `Transaction`, `transaction(path @body timeout=100ms)`, and `tx.execute(sql parameters)`. It owns connection/begin, calls the body with `@tx`, and commits on a successful body outcome, rolls back on a failure. A commit error still attempts rollback if the driver says it is active. When commit success is uncertain, `CommitUnknown` is an error; the adapter does not falsely certify rollback or safe retry. SQL is parameterized, and a body can return errors like InsufficientFunds without an explicit rollback action. A callback that returns `none` succeeds. A record containing an error is data and does not automatically trigger rollback.

## C/FFI example boundaries

Program 09's final PCRE2 wrapper uses the real `_8` ABI on a 64-bit target, the default allocator (`context=none`), and a privately captured move-only Code owner. Its local nominal helper has the same lifecycle protocol as a module nominal record; it is hidden by lexical binding, not by inventing `private` or `opaque`. The caller gets an owning callable, not the raw pointer or a public record constructor. A nongeneric closure can already capture/move an owner. The example exposes capture-count querying to show a real use after acquisition, not a fake API that only allocates and frees.

**Frontend capability, verified absent by source inspection:** `compiler/dewy_reader_seed.jo:6544–6557` accepts a local plain record/alias but leaves a local nominal type unread; its local-method checker at 5848–5856 rejects methods on local types. The self-hosted reader does likewise (`compiler/dewy_reader.dewy:6847`). `tests/cases/object/local_type.dewy:2` and its `.err:1` pin the rejection. No compiler was run and no checkout file was changed.

The final proposal therefore includes one explicit, limited frontend capability: allow the existing `let Name:type = type of [fields ... hooks ...]` declaration in a lexical function scope, with closed hook bodies (own fields and existing module functions, no captured runtime locals). Give it one compile-time nominal identity per lexical declaration/concrete generic instance, not a new runtime type on every invocation. Use existing lifecycle summaries and normal private closure captures; no new keyword, visibility tag or runtime cost. Ordinary plain local records cannot own a C handle because their hook methods are currently rejected; a public module record exposes a forgeable raw constructor. That is the demonstrated existing-construct failure that justifies this addition. It is a design proposal requiring implementation, not a claim that the sample compiles today. The completeness grade remains 4 for that real dependency. Safe wrappers that require richer method-bearing public interfaces still need actual encapsulation rather than a public raw pointer field; this round only demonstrates the small callable-handle route.

`pcre_free` carries a trusted extern row excluding panic/allocation/blocking, using the existing rule in LANGUAGE.md:4620–4625 that rows on extern declarations are unsafe claims. It is justified only for this default-allocator path. User-supplied deallocation callbacks would invalidate the claim unless separately checked. A production binding also models ABI widths per target and supplies useful compile-error payloads. A no-trusted-library/prove-drop-cannot-fail mode rejects an unproved C cleanup claim; this round does not waive that gate.

The abandoned curl sketch was wrong as a universal no-fail release example: curl cleanup can invoke configured callbacks or perform protocol shutdown despite returning C void. It also exported forgeable raw owner records and its unused owner would die before the status print. Replacing it with this smaller bounded wrapper avoids claiming that a C void signature establishes a cleanup contract.

Primary C API references: [PCRE2 compile](https://www.pcre.org/current/doc/html/pcre2_compile.html), [code free](https://www.pcre.org/current/doc/html/pcre2_code_free.html), [pattern info](https://www.pcre.org/current/doc/html/pcre2_pattern_info.html). The callback/shutdown limitation of the rejected example is documented by [curl_easy_cleanup](https://curl.se/libcurl/c/curl_easy_cleanup.html).

## Runtime and compiler cost requirements

- Non-shared scalar owner: one known release call at end of lifetime, usually inlined; no tracing, GC, registration allocation, mandatory vtable or mandatory heap guard. Task cancellation/panic registration uses existing cleanup plans and only where obligations exist.
- Shared queue/asset identity: reference/capability counts, often atomic across tasks; last-drop wakeup/fence retirement may be observable. Endpoint splitting changes a count. Actual counts/orderings depend on queue implementation; do not promise lock-free last-drop wakeups universally.
- Containers: O(number of live owner elements), plus recursive fields. Prefix/tag/live-state bookkeeping is only needed for dynamic partial construction/control flow. No new per-element compiler dataflow pass.
- Fallible scoped calls: direct callback call (often inline), state for completion, conditional shield/deadline handling, a union result. The final runner establishes a shield only on the cancellation path; normal completion gets no arbitrary 100 ms deadline. Pair allocation/boxing follows existing payload representation and allocation-failure policy; never advertise that error composition is always allocation-free. O(number of reported failures), existing environmental policy if reporting storage is exhausted. Normal success does not allocate a cleanup error tree.
- Finalization can block and can take multiple grace periods. Warnings at the acquisition site must identify finalizer, default/explicit cancellation-finalization grace, unknown foreign blocking, possible retained GPU/audio memory, and visible channel atomic-count costs when material. Warn once per source operation/instantiation, not once per element. The strict cost lane diagnoses unadmitted allocation or opaque costs as it already does.
- Compiler work reuses indexed lifecycle/call summaries. Validate each reachable concrete resource/hook once. Run no-escape/liveness only at resource obligations, and the existing ownership budget/conservative fallback still applies. No new whole-program solver for arbitrary missing cleanup actions. Required implementation gates include the flagship instruction-count panel; no speed win/cost estimate has been measured here.

## Concrete late-flush scenario

Program 01 has a `--flush-error` mode: prepare a three-byte source inside the scoped temp directory, copy it into a buffered File opened on Linux `/dev/full`, then reach EOF. The intermediate write is buffered; native flush at completion reports FileError for ENOSPC. If source setup or opening the device itself fails, that is a different earlier error; the paper trace assumes those succeed and does not claim to have observed the failure at runtime. No device is created, and no program was executed. The kernel-device behavior is documented by [Linux full(4)](https://man7.org/linux/man-pages/man4/full.4.html). This also makes the difference between accepting buffered bytes and completing a copy concrete.

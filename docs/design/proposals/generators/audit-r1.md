# Generator sketch audit, round 1

Reviewed sketch §§1–25 and its cleanup addendum against Dewy at `44e29198e`. The accepted decisions take precedence over older discussion and archived wording. D39, D40, D42 and D44 questions cited below remain open where indicated. Current compiler behavior is checked against the reader, checker and existing fixtures by inspection.

## Must settle

1. **Must settle · §§1, 3, 7 — Variable-count eager bindings.** The October 23 multi-expressions decision says “a binding holds a fixed number” and directs loop and branch outputs to a collector. The compiler has a rejection fixture for exactly this kind of loop/branch output in a binding. `variable`, `values`, and the eager `xs` in §7 require holding a count determined when the initializer runs. Keep fixed-count bindings and use an eager array for a changing count, or explicitly revise the binding rule to support finite shape unions. §7 would also need a rule for loop counts inferred from bounds. [docs/design/decisions.md:41](../../../../docs/design/decisions.md:41), [docs/design/multi_expressions.md:105](../../../../docs/design/multi_expressions.md:105), [tests/cases/multi/values_block_branch.dewy:1](../../../../tests/cases/multi/values_block_branch.dewy:1)

2. **Must settle · §§2–3 and the overview — Static positional arity.** Substitution invariance specifies “one that varies cannot fill parameters (collect it)” and “Overloads see the expanded shape.” The proposed rejection of `add(variable)` is consistent, but the general “consumer handles every possible shape” rule would admit a call with several equally valid runtime arities. Today's overloads may have different arities and are selected from the statically expanded call. The archived reference also says “ordinary overload resolution is static” and describes runtime multifunction values as provisional. Keep variable-shape consumption in collectors and explicit matches, or decide that an exhaustive arity dispatch is a new kind of call. Preserve static overload selection as the default. [docs/design/multi_expressions.md:202](../../../../docs/design/multi_expressions.md:202), [docs/LANGUAGE.md:329](../../../../docs/LANGUAGE.md:329), [docs/LANGUAGE.md:498](../../../../docs/LANGUAGE.md:498), `archive/master-pre-restart:site/reference/src/functions-and-calls.md:185–194`

3. **Must settle · §§1–3, 8, 16–17, 22–23 — Heterogeneous groups and function results.** “A group's values may have different types,” and the whole type of a binding can name such a group. The written `:>(int64 int64)` contract fixes count and type, and “The values share one type for now.” The existing inferred-body fixture also rejects mixed expressed types. A group type is restricted to a whole binding or function result, so it cannot simply be used as an array element, a parameter, or a first-class variant of a shape union. Decide whether heterogeneity is confined to groups and streams of single union-typed values, or also changes ordinary multi-valued function contracts and calls through `@f`. A boxed per-position array `[T U]` already gives one heterogeneous value with positional types. [docs/design/multi_expressions.md:147](../../../../docs/design/multi_expressions.md:147), [docs/design/multi_expressions.md:173](../../../../docs/design/multi_expressions.md:173), [docs/design/multi_expressions.md:224](../../../../docs/design/multi_expressions.md:224), [tests/cases/multi/mixed_types.err:1](../../../../tests/cases/multi/mixed_types.err:1), [docs/design/decisions.md:119](../../../../docs/design/decisions.md:119), [docs/LANGUAGE.md:2683](../../../../docs/LANGUAGE.md:2683)

4. **Must settle · §§2, 8, 10, 12 and 15 — Proof and evaluation for generator spreads into fixed calls.** The accepted call rule says an array spread's “length must fit,” with proof or an opt-in runtime check at a one-version call. Arguments also run in written order. `add(gen...)` needs proof of two flattened outputs, and a general stream may be unbounded or may fail or do work before revealing that its output count is wrong. Reuse the static proof for a simple `lazy (1 2)`. Require a proven finite, exact output count for ordinary fixed calls in the first version, or deliberately specify a checked/fallible path and its effect order, including any extra advance needed to detect excess. The obligation counts the full flattened output exactly, regardless of the number of suspension steps. [docs/design/multi_expressions.md:206](../../../../docs/design/multi_expressions.md:206), [docs/design/no_traps.md:58](../../../../docs/design/no_traps.md:58), [docs/LANGUAGE.md:329](../../../../docs/LANGUAGE.md:329)

5. **Must settle · §§10, 13, 16, 22–23, 25 — What one advancement returns.** The flattening rule gives the example “`((1 2) 3)` is three values.” The provisional `next` returns “the next element or `none`,” and a loop binds one value. Per-value advancement preserves those rules. Group-preserving advancement adds an observable boundary where substitution and calls currently flatten the group. It needs a one-value representation or an explicit new step protocol and rules for which groups survive blocks, calls, branches and delegation. Either option needs to skip `void` and distinguish an emitted `none` from exhaustion if the step type admits it. Start with per-value iteration and a per-position array for an atomic pair, or choose group-preserving steps explicitly and carry a completion discriminator through the public step interface. [docs/design/multi_expressions.md:13](../../../../docs/design/multi_expressions.md:13), [docs/design/multi_expressions.md:32](../../../../docs/design/multi_expressions.md:32), [docs/design/multi_expressions.md:224](../../../../docs/design/multi_expressions.md:224), [docs/LANGUAGE.md:5014](../../../../docs/LANGUAGE.md:5014), [docs/LANGUAGE.md:5034](../../../../docs/LANGUAGE.md:5034), [compiler/checker_iterator_rewrites.dewy:110](../../../../compiler/checker_iterator_rewrites.dewy:110)

6. **Must settle · §§2, 8–12, 16, 19, 21 — Who owns and advances the suspended state.** Value semantics say that “ordinary rebinding behaves as an independent value.” The accepted iterator-control idiom is `loop x in @it`, and the guide says `loop x in it` “steps a copy of the iterator.” “Consumes” is underspecified for ordinary `loop`, `...` and delegation. Silently sharing progress through assignment conflicts with value semantics. Blindly copying a frame can duplicate a move-only capture, a live resource or a registered action. Decide whether a generator is move-only or conditionally copyable and what plain loop/spread owns. Use a single owner by default for frames with cleanup duties, and explicitly distinguish consuming a temporary, advancing a named place and copying a copyable cursor. Define what another loop over the same binding sees. [docs/design/value_semantics.md:3](../../../../docs/design/value_semantics.md:3), [docs/design/decisions.md:155](../../../../docs/design/decisions.md:155), [docs/LANGUAGE.md:5014](../../../../docs/LANGUAGE.md:5014), [docs/LANGUAGE.md:2159](../../../../docs/LANGUAGE.md:2159), [docs/LANGUAGE.md:2243](../../../../docs/LANGUAGE.md:2243)

7. **Must settle · §24 — Places crossing an advance.** Accepted place-returning methods lend a receiver route under a lexical check. The returned place “cannot be re-placed, captured or returned,” and an escaping callback over a mutable iteration element captures an independent snapshot. Producing `@x` to an ordinary collector or carrying it over the next advance would generalize these rules. Advancing or dropping the source can retire the current slot or release the owner and its guard. Emit values in the first version. If lending is needed, specify a place valid only for the consumer's step, with static checks preventing escape, conflicting advancement or replacement, and use of a dead owner. Ordinary arrays of outputs and ordinary `next` results cannot silently store such places. [docs/design/decisions.md:52](../../../../docs/design/decisions.md:52), [docs/design/ownership.md:236](../../../../docs/design/ownership.md:236), [docs/design/ownership.md:252](../../../../docs/design/ownership.md:252), [docs/LANGUAGE.md:5091](../../../../docs/LANGUAGE.md:5091)

8. **Must settle · §§6, 8–12, 15, 17–18, 21 — Effect attribution.** Declared rows are “contracts callers see.” The effects design says “creation costs are distinct from invocation effects” and includes “lifecycle, defaults, conversions, closure construction/copy and defer/cleanup edges.” Deferring effects without carrying them into the returned generator's contract would allow a consumer to hide `blocks`, `panics`, allocation or shared mutation behind a factory or callback. Charge construction for real capture/move/copy/frame costs and advancement for body, delegated and callback costs. Charge completion/drop for cleanup, including when implicit. Check blocking, panic and cost exclusions where the operations can actually run, including a spread or a loop doing implicit advancement. Distinguish synchronous suspension from a wait that may block. [docs/design/decisions.md:74](../../../../docs/design/decisions.md:74), [docs/design/effects.md:13](../../../../docs/design/effects.md:13), [docs/design/effects.md:35](../../../../docs/design/effects.md:35), [docs/design/effects.md:49](../../../../docs/design/effects.md:49), [docs/design/effects.md:98](../../../../docs/design/effects.md:98), [docs/LANGUAGE.md:730](../../../../docs/LANGUAGE.md:730)

9. **Must settle · §§12, 19–21 and cleanup addendum — Observable failure when a suspended computation ends.** Accepted D40 Q1 says “a cleanup failure is the function's result,” with visible cleanup in tooling. The older ownership spec's ordinary drop hooks cannot forward errors. D40 also accepts an explicit abandon role. Inferring that advancing, breaking or dropping a generator simply ends it can lose a fallible close after values already escaped, or require a hidden exit from the consumer. Decide where the terminal failure is available on normal completion, delegation and early exit, and whether fallible automatic drop is supported. Keep an ordinary infallible drop path, require an explicit checked completion/close path if needed to honor D40, and specify what remains visible if the body also fails. D40 Q6 and D42 still govern the details of visible exits and combined failures. ## Adjust sketch

10. **Adjust sketch · §3 — Sequence `match` already exists.** The guide demonstrates “`match (x y) (a:int64 <string>) => a`” and describes length and element tests for array patterns. The fixture also uses a braced arm list. The typed parenthesized arms in the sketch are in the existing form. The new part is the unboxed variable-count scrutinee and its coverage/type representation. Keep the pattern syntax. For an existing example, match a collected array by length with a fallback, or use a closed union of named variants with fixed payload shapes and match by variant. Existing totality still requires every shape/member to be covered. 11. **Adjust sketch · §4 — Prefix rest is contextual.** An attached `...rest:T` collects leftover positional arguments “into an array of `T`.” Later parameters are keyword-only. A spaced bare `...` is a separator. Rest is homogeneously typed. Unpacking has its own contextual rest, whose remainder can stay several values. General prefix collection would extend the grammar beyond those contexts. Show `forward = (...args:int) => add(args...)` with exactly two arguments at the specialization, or a length proof for any dynamic spread. Scope “collects into” to the named contexts. ## Notes

21. **Note · §§11–12, 18–21 and cleanup addendum — Cancellation across source and consumer.** D44 Q5 asks whether “a loop over any source … end[s] when its task is canceled,” with `or_throw` after the source to propagate instead. The live guide documents older source-specific behavior, and the later D4 Q1 decision reverses the old blanket treatment in `??`. Current cancellation is cooperative. The guide says “an arbitrary computation is not forcibly terminated.” Specify that synchronous advancement participates in the advancing work's context, and what a canceled delegated wait does to the inner and outer generator. If D44 Q5 is accepted, use loop termination by default and the explicit forwarding form. Keep cancellation separate from EOF and from a data element at the protocol boundary. A loop that can run indefinitely before an output or a wait needs separate cooperative cancellation semantics.
